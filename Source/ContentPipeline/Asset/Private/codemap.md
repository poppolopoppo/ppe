# Source/ContentPipeline/Asset/Private/

## Responsibility
The Asset/Private folder contains the implementation details of the ContentPipeline Asset library, including concrete importer specializations, serializer logic, and the FContentImporterException type used for type mismatch enforcement. It houses the concrete implementations of the importer and processor templates declared in Asset/Public/, providing the actual source-to-intermediate and intermediate-to-output transformation logic that is hidden behind the public API abstraction boundary. This folder also contains any internal utility types and helper classes required by the asset toolchain implementation, ensuring that module consumers depending only on Asset/Public/ headers are not exposed to implementation details.

## Design
The private implementation follows the same template-based design as the public API, with TContentImporter<_Import> and TContentProcessor<_Process> specializations for each asset type. FContentImporterException derives from std::runtime_error and is thrown when type mismatches are detected during dynamic cast dispatch. The private folder implements the actual source file reading, intermediate data generation, and asset artifact serialization logic that was declared purely abstract in the public headers. META_DYNAMIC_CASTABLE_IMPL is used on all concrete importer and processor types for runtime type identification. The folder enforces the API boundary by keeping all implementation details hidden from Source/ContentPipeline/Asset/Public/, with only the exception type and template declarations crossing the boundary. Static initialization order is managed through the TContentToolchain::Initialize() cycle, and all concrete types are registered with the content toolchain during module startup.

## Flow
Concrete importers implement IContentImporter::Import(ctx, dst) by reading source files, performing format-specific conversion, and producing intermediate data at the destination path. Concrete processors implement IContentProcessor::Process(ctx, dst) by transforming intermediate data into the final asset format, with serialization writing the output artifact to disk. The FContentImporterContext injects the source directory, dependency list, and intermediate output path at import time, while FContentProcessorContext provides intermediate path and output parameters. Serialization context injects the final artifact path and format parameters. Error handling throws FContentImporterException on type mismatch, and successful completion records dependencies through the context system for BuildGraph DAG tracking. The private folder's types are instantiated by TContentToolchain during the Import() → Process() → Serialize() pipeline, with each concrete type handling its specific asset format's conversion requirements.

## Integration
Asset/Private integrates with Source/ContentPipeline/Asset/Public/ which declares the abstract interface and template types that Asset/Private/ implements, with Source/ContentPipeline/BuildGraph/ for DAG-based build node tracking where concrete importer/procesor nodes are registered using the public API types, with Source/ContentPipeline/Asset/Public/ headers consumed by the implementation, and with Source/ContentPipeline/MeshBuilder/Private for mesh importer implementation details where private mesh importer specializations live. Specific paths include Source/ContentPipeline/Asset/Private/ implementation files included by Source/ContentPipeline/BuildGraph/ for node creation, Source/ContentPipeline/MeshBuilder/Private for mesh importer implementations that depend on the private asset types, and Source/ContentPipeline/Asset/Private headers included by any folder needing concrete importer/procesor behavior beyond the public API boundary.
