# Source/ContentPipeline/Texture/

## Responsibility
The Texture folder provides the texture content pipeline infrastructure, handling the import, processing, compression, and serialization of texture assets. It defines the texture data types and metadata structures (FTextureSource, FTextureSourceProperties) that encapsulate dimensions, format, gamma settings, and flags, and manages the block compression pipeline (DXT1/DXT5) with color mask detection for format selection. The folder provides type-safe routing for texture source assets through the content toolchain, enabling DAG-based build node registration in the BuildGraph system for scan/build/clean orchestration, and ensuring that texture assets can be tracked through the full content build lifecycle with proper dependency resolution and revision tracking.

## Design
Texture processing follows the established template-based pattern with TContentImporter<_Import> and TContentProcessor<_Process> specializations, leveraging META_DYNAMIC_CASTABLE_IMPL for runtime type identification of texture importers and processors. The folder declares FTextureSource for texture metadata (dimensions, format, gamma, flags) and FTextureSourceProperties for dimensions, format, gamma, and flags. Block compression uses DXT1 for RGB sources and DXT5 for RGBA sources, with color mask detection guiding format selection. Mip chain validation (HasFullMipChain2D()) ensures proper mipmap generation. The Public/Private folder splitting within Texture separates the texture API surface from implementation details, with texture format definitions and source metadata structures exposed through Public headers, while concrete importer and processor implementations reside in Private directories.

## Flow
Texture data flow begins with source asset detection, proceeds through TContentToolchain::Import which dispatches to the appropriate texture IContentImporter::Import(ctx, dst), converting source image files into the engine's internal texture format. The intermediate data then flows through TContentProcessor::Process(ctx, dst) which calls Compress(dst, src, quality) → BlockCompress_<DXT1/DXT5>() for block compression. Color mask detection determines format selection (RGB→DXT1, RGBA→DXT5). Mip chain validation (HasFullMipChain2D()) ensures proper mipmap generation. Finally, serializers produce the persistent texture artifact. Each stage records dependencies via context injection, and the BuildGraph folder tracks texture build nodes through the three-phase pipeline. The Texture.Private.Texture/ folder provides concrete texture processor implementations, while Texture.Public/ exposes the type definitions and API surface.

## Integration
Texture integrates with Source/ContentPipeline/BuildGraph/ for DAG-based build node registration of texture pipeline nodes, with Source/ContentPipeline/Asset/Public for the abstract toolchain interface and template types, with Source/ContentPipeline/MeshBuilder/Public for mesh-texture material coordinate coordination, with Source/ContentPipeline/PipelineCompiler/ for compiled shader output when texture bindings are involved, and with Source/ContentPipeline/Asset.Texture/ for texture asset type specialization. Specific paths include Source/ContentPipeline/Texture/Public/Texture for public texture API, Source/ContentPipeline/Texture/Private/Texture for texture backend implementation, Source/ContentPipeline/Texture/Private/Texture/Compression for compression implementations, Source/ContentPipeline/Texture/Private/Texture/Image for image processing implementations, and Source/Runtime/RHI/ for texture backend RHI integration.
