# Source/ContentPipeline/

## Responsibility
The ContentPipeline root orchestrates the entire content build system, coordinating the BuildGraph DAG execution engine, MeshBuilder import tools, Texture processing pipeline, PipelineCompiler shader compilation, PipelineReflection metadata extraction, and Asset library management. It serves as the top-level entry point for all content pipeline operations, integrating with the modular domain framework and providing the FBuildEnvironment that holds platform services, cache, executor, and logging infrastructure for the full content build lifecycle.

## Design
The folder implements a modular domain architecture with FModularDomain driving module lifecycle, complemented by DAG-based build orchestration via FBuildGraph and FBuildNode. The three-phase pipeline (Scan → Build → Clean) is managed through dedicated context objects (FScanContext, FBuildContext, FCleanContext). TContentToolchain defines the concrete toolchain execution flow, while FAbstractContentToolchain provides the abstract interface. Template-based type-safe importers (TContentImporter<_Import>) and processors (TContentProcessor<_Process>) enable runtime type dispatch via META_DYNAMIC_CASTABLE_IMPL. The Public/Private folder splitting enforces API boundaries, with Public headers exposing the interface and Private directories containing implementation details. FBuildRevision provides revision tracking for incremental builds, and compare_exchange_weak ensures atomic result aggregation across parallel execution.

## Flow
Content pipeline operations begin with BuildRobot or BuildGraph-driven graph construction, where ScanAll() discovers all build nodes and populates the DAG with dependency edges. ScanNodes_() invokes FScanContext::Scan() on each node, followed by BuildAll() which triggers FBuildContext::Build() calling node.Import() → node.Process() for each registered node. After building, CleanAll() runs FCleanContext::Clean() to release intermediate resources. The IBuildExecutor::QueueAndWaitFor() method parallelizes node execution across workers, while IBuildCache::HasArtifact() determines whether output is already cached and up-to-date. Dependency tracking flows through StaticDeps() → DynamicDeps() → RuntimeDeps(), with output file tracking via AddFiles() after each scan phase. Pipeline compilation flows through FVulkanPipelineCompiler::Compile() for each pipeline type, with GLSL → SPIR-V → shader module conversion handled by FVulkanSpirvCompiler. Pipeline reflection decisions consult PipelineReflection for metadata-driven build choices.

## Integration
The ContentPipeline root integrates with all ContentPipeline modules and the Runtime framework. It references Source/ContentPipeline/BuildGraph/ for the DAG execution engine, Source/ContentPipeline/MeshBuilder/ for mesh import integration, Source/ContentPipeline/Asset.Geometry/ for geometry asset specialization, Source/ContentPipeline/Asset.Texture/ for texture processing, Source/ContentPipeline/Texture/ for texture backend operations, Source/ContentPipeline/PipelineCompiler/ for shader compilation, Source/ContentPipeline/PipelineReflection/ for reflection-driven decisions, and Source/ContentPipeline/Asset/ for the asset library core. Specific paths include Source/ContentPipeline/BuildGraph/Public/ for the IBuildExecutor API, Source/ContentPipeline/BuildGraph/Private/ for context implementation, Source/ContentPipeline/MeshBuilder/Public/Mesh/ for mesh format definitions, Source/ContentPipeline/Texture/Public/Texture for public texture API, Source/ContentPipeline/Texture/Private/Texture for private texture implementation, Source/ContentPipeline/PipelineCompiler/Public/Vulkan for Vulkan pipeline compilation, and Source/ContentPipeline/PipelineReflection/Public for reflection interfaces. The root also connects to Source/Runtime/Application/ for application-level integration and Source/Tools/IODetouring/ for IO tracing support.
