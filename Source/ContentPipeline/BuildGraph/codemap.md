# Source/ContentPipeline/BuildGraph/

## Responsibility
The BuildGraph folder orchestrates the DAG-based asset build execution engine, managing the three-phase pipeline of Scan → Build → Clean across all ContentPipeline modules. It defines FBuildGraph as the directed acyclic graph of build nodes, FBuildNode as the base class for individual pipeline steps, FBuildContext and FScanContext for the build and scan phases respectively, FCleanContext for cleanup operations, and FBuildEnvironment as the holder of platform, cache, executor, and logging services. The folder's executor interface IBuildExecutor parallelizes node execution, while IBuildCache provides artifact caching and IBuildLog provides structured logging throughout the pipeline. It serves as the central coordination point for all content asset builds, ensuring that dependency edges are properly tracked, revision-aware re-execution occurs only when source dependencies have changed, and parallel execution is efficiently scheduled across available workers.

## Design
The three-phase pipeline architecture is the cornerstone of this folder's design: ScanAll() discovers and appends all build nodes to the graph, ScanNodes_() invokes FScanContext::Scan() on each node, then BuildAll() triggers FBuildContext::Build() for each node's Import() and Process() steps, and CleanAll() runs FCleanContext::Clean() for resource reclamation. Revision tracking via FBuildRevision ensures that node re-execution occurs only when source dependencies have changed. The atomic result aggregation pattern using compare_exchange_weak prevents race conditions during parallel build execution, and HasStopOnError() configures whether the pipeline halts on the first build failure. The DAG structure supports node discovery via AppendNodes(transaction) for meta-transaction boundaries, and output file tracking via AddFiles() after scan completes. The IBuildExecutor interface abstracts the parallel execution model, allowing different implementations (thread pool, worker queue) to be swapped without affecting the graph logic. IBuildCache::HasArtifact() determines whether a node's output is already cached and up-to-date, enabling incremental builds. The folder's design enforces separation of concerns between graph structure (FBuildGraph), per-node execution (FBuildContext), and system services (FBuildEnvironment).

## Flow
The pipeline begins with ScanAll(), which iterates over all registered build nodes and calls each node's Scan() method. This populates the graph with dependency edges and marks nodes as ready for building. BuildAll() then iterates over the graph, invoking FBuildContext::Build() on each node, which in turn calls node.Import() → node.Process(). After building, CleanAll() runs FCleanContext::Clean() on each node to release intermediate resources. The IBuildExecutor::QueueAndWaitFor() method parallelizes node execution across available workers, and IBuildCache::HasArtifact() determines whether a node's output is already cached and up-to-date. Dependency tracking flows through StaticDeps() → DynamicDeps() → RuntimeDeps(), with output file tracking via AddFiles() after each scan phase. The three-phase cycle (Scan → Build → Clean) repeats for each build invocation, with revision checks determining which nodes need re-execution. Pipeline compilation flows through FVulkanPipelineCompiler::Compile() for each pipeline type, called from within node.Process() when shader compilation is required.

## Integration
BuildGraph integrates directly with every other ContentPipeline module. It references Source/ContentPipeline/Asset/ for asset-level build node registration, where asset build nodes are registered using the public API types. It references Source/ContentPipeline/MeshBuilder/ for mesh build nodes, where mesh import and processing nodes are tracked through the DAG. It references Source/ContentPipeline/Asset.Geometry/ for geometry build nodes, where geometry pipeline nodes are registered. It references Source/ContentPipeline/Asset.Texture/ for texture build nodes, where texture processing nodes are tracked. It references Source/ContentPipeline/Texture/ for texture-specific build logic and compression nodes. It references Source/ContentPipeline/PipelineCompiler/ for pipeline compilation build nodes, where shader compilation is orchestrated through the build graph. It references Source/ContentPipeline/PipelineReflection/ for reflection-driven build decisions, where reflection metadata influences build node scheduling. Specific paths include Source/ContentPipeline/BuildGraph/Public/ for the IBuildExecutor API consumed by all ContentPipeline modules, Source/ContentPipeline/BuildGraph/Private/ for context implementation details and context classes, Source/ContentPipeline/BuildGraph/Public/BuildExecutor.h for the IBuildExecutor interface, and Source/ContentPipeline/BuildGraph/ as the central dependency for all ContentPipeline build orchestration.
