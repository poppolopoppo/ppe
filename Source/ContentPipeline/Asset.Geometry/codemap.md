# Source/ContentPipeline/Asset.Geometry/

## Responsibility
The Asset.Geometry folder specializes geometry asset types within the ContentPipeline, handling the import, processing, and serialization of geometry data meshes and formats. It defines geometry-specific importer and processor types that integrate with the TContentToolchain framework, enabling DAG-based build node registration in the BuildGraph system for scan/build/clean orchestration. The folder provides type-safe routing for geometry source assets through the content toolchain, supporting mesh import from source formats into the engine's internal mesh representation, and ensuring that geometry assets can be tracked through the full content build lifecycle with proper dependency resolution and revision tracking.

## Design
Geometry asset processing follows the template-based pattern established by TContentImporter<_Import> and TContentProcessor<_Process>, with geometry-specific specializations registered through the content toolchain. The folder leverages META_DYNAMIC_CASTABLE_IMPL for runtime type identification of geometry importers and processors, enabling dynamic dispatch within the content toolchain's Import() and Process() stages. FContentImporterContext and FContentProcessorContext inject geometry-specific source directories, dependency lists, and intermediate output paths. The geometry pipeline integrates with the MeshBuilder subsystem for mesh import operations, and with the BuildGraph DAG for build node lifecycle management. Geometry types support revision tracking via FBuildRevision, ensuring incremental builds only re-process source geometry when dependencies change. The Public/Private folder splitting within Asset.Geometry separates the geometry API surface from implementation details, with geometry format definitions and mesh data structures exposed through Public headers.

## Flow
Geometry data flow begins with source asset detection, proceeds through TContentToolchain::Import which dispatches to the appropriate geometry IContentImporter::Import(ctx, dst), converting source mesh files (FBX, OBJ, etc.) into the engine's internal mesh format. The intermediate mesh data then flows through TContentProcessor::Process(ctx, dst) for any required post-processing (normal generation, tangent calculation, LOD setup). Finally, serializers produce the persistent geometry artifact. Each stage records dependencies via context injection, and the BuildGraph folder tracks geometry build nodes through the three-phase pipeline. The MeshBuilder.Private/ folder provides concrete geometry importer implementations, while Asset.Geometry.Public/ exposes the type definitions and API surface.

## Integration
Asset.Geometry integrates with Source/ContentPipeline/BuildGraph/ for DAG-based build node registration of geometry pipeline nodes, with Source/ContentPipeline/MeshBuilder/Public for mesh importer integration where geometry importers depend on mesh format definitions, with Source/ContentPipeline/Asset/Public for the abstract toolchain interface and template types, with Source/ContentPipeline/Asset.Texture/ for geometry-texture coordination (mesh materials often reference texture assets), and with Source/ContentPipeline/PipelineCompiler/ for compiled pipeline output when geometry shaders are involved. Specific paths include Source/ContentPipeline/Asset.Geometry/Public for geometry type API, Source/ContentPipeline/Asset.Geometry/Private for geometry importer implementations, Source/ContentPipeline/MeshBuilder/Public/Mesh for mesh format dependencies, Source/ContentPipeline/Asset.Geometry/Public/Interop for cross-format geometry interop references, and Source/ContentPipeline/MeshBuilder/Private/Mesh for concrete geometry importer implementations.
