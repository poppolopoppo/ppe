# Source/ContentPipeline/Asset.Texture/

## Responsibility
The Asset.Texture folder specializes texture asset types within the ContentPipeline, handling the import, processing, and serialization of texture data. It defines texture-specific importer and processor types that integrate with the TContentToolchain framework, enabling DAG-based build node registration in the BuildGraph system for scan/build/clean orchestration. The folder provides type-safe routing for texture source assets through the content toolchain, supporting texture compression and format conversion, and ensuring that texture assets can be tracked through the full content build lifecycle with proper dependency resolution and revision tracking.

## Design
Texture asset processing follows the template-based pattern established by TContentImporter<_Import> and TContentProcessor<_Process>, with texture-specific specializations registered through the content toolchain. The folder leverages META_DYNAMIC_CASTABLE_IMPL for runtime type identification of texture importers and processors, enabling dynamic dispatch within the content toolchain's Import() and Process() stages. FContentImporterContext and FContentProcessorContext inject texture-specific source directories, dependency lists, and intermediate output paths. The texture pipeline integrates with the BuildGraph DAG for build node lifecycle management, and with the Texture subsystem for compression and backend formatting. Texture types support revision tracking via FBuildRevision, ensuring incremental builds only re-process source textures when dependencies change. The Public/Private folder splitting within Asset.Texture separates the texture API surface from implementation details, with texture format definitions and source metadata structures exposed through Public headers.

## Flow
Texture data flow begins with source asset detection, proceeds through TContentToolchain::Import which dispatches to the appropriate texture IContentImporter::Import(ctx, dst), converting source image files into the engine's internal texture format. The intermediate data then flows through TContentProcessor::Process(ctx, dst) for compression via Compress(dst, src, quality) → BlockCompress_<DXT1/DXT5>(), with format selection based on color mask detection (RGB→DXT1, RGBA→DXT5). Mip chain validation (HasFullMipChain2D()) ensures proper mipmap generation. Finally, serializers produce the persistent texture artifact. Each stage records dependencies via context injection, and the BuildGraph folder tracks texture build nodes through the three-phase pipeline. The Texture.Private.Texture/ folder provides concrete texture processor implementations, while Asset.Texture.Public/ exposes the type definitions and API surface.

## Integration
Asset.Texture integrates with Source/ContentPipeline/BuildGraph/ for DAG-based build node registration of texture pipeline nodes, with Source/ContentPipeline/MeshBuilder/Public for mesh-texture material coordination, with Source/ContentPipeline/Asset/Public for the abstract toolchain interface and template types, with Source/ContentPipeline/PipelineCompiler/ for compiled shader output when texture bindings are involved, and with Source/ContentPipeline/Texture/ for texture backend operations and compression. Specific paths include Source/ContentPipeline/Asset.Texture/Public for texture type API, Source/ContentPipeline/Asset.Texture/Private for texture processor implementations, Source/ContentPipeline/Texture/Public/Texture for public texture API, Source/ContentPipeline/Texture/Private/Texture for texture backend implementation, Source/ContentPipeline/Texture/Private/Texture/Compression for compression implementations, and Source/ContentPipeline/Texture/Private/Texture/Image for image processing implementations.
