# Source/

## Responsibility
The Source/ folder is the root aggregator for all engine source code in PPE. It organizes the entire codebase into hierarchical modular directories: Runtime/, Extensions/, ContentPipeline/, Tools/, and Programs/. Each top-level subfolder has a well-defined role in the engine architecture, with Source/ serving as the entry point for all C++ source files (1,505 files, ~286K lines). The folder structure follows the modular system where each subsystem declares its interface in `*-module.json` files consumed by the Go-based build system. Source/ enables cross-cutting concerns like the fiber-based task scheduler, custom allocators (36 types), and the type-safe service registry (FModularServices) that supports parent-child scoping for dependency injection.

## Design
Source/ employs a hierarchical modular design with strict dependency ordering. The top-level directory contains 5 aggregate folders: Runtime provides core engine libraries (Core, Application, RHI, RTTI, Serialize, VFS, Network, Remoting), Extensions offers pluggable backends (RHIVulkan, ApplicationUI), ContentPipeline handles asset processing (BuildGraph, MeshBuilder, PipelineCompiler, PipelineReflection, Texture), Tools supplies developer utilities (IODetouring, IOWrapper), and Programs contains standalone executables (BuildRobot, ShaderToy, VoxelCube, WindowTest, UnitTest, IOWrapperTest). Each subfolder follows the module lifecycle pattern (Start → PostStart → DutyCycle → PreShutdown → Shutdown) and communicates through FModularServices. The design uses C++ templates, CRTP, expression templates, and macro-based code generation extensively, with zero STL in hot paths and custom allocators for every access pattern. Module anchors via `extern "C"` function pointers enable cross-DLL discovery.

## Flow
Source/ acts as the top-level conduit through which all source code flows during build and runtime. The Go build system reads module declarations from `*-module.json` files across all subfolders, generates `BuildModules.generated.h` with static/dynamic registration code, dependency lists, and DLL import/export symbols. Source code moves from individual module folders through the build system, which handles unity builds per module, HAL-aware file exclusion, and module anchor patterns. At runtime, modules initialize in dependency order (controlled by LoadOrder in module JSON), with Core starting first as the foundation, followed by Application, RHI, RTTI, Serialize, VFS, Network, and Remoting. Extensions (RHIVulkan, ApplicationUI) load dynamically and register with the modular services. ContentPipeline modules process assets through the BuildGraph DAG, and Programs execute their specific demonstrations using the initialized runtime subsystems.

## Integration
Source/ integrates all top-level source directories and their submodules into a cohesive engine architecture. Runtime/ connects to Extensions/ (RHIVulkan implements RHI for Vulkan, ApplicationUI provides ImGui-based UI), ContentPipeline/ (asset processing feeds all Programs), Tools/ (IODetouring intercepts file operations for debugging, IOWrapper supports distributed builds), and Programs/ (executables that consume runtime and tools services). Specific paths: Source/Runtime/Core/ provides foundational containers and math used by Source/Extensions/ApplicationUI/, Source/Runtime/VFS/ supports path resolution for Source/ContentPipeline/, Source/Runtime/Network/ and Source/Runtime/Remoting/ enable networked features used by Source/Programs/, Source/Tools/IODetouring/ hooks into Source/Runtime/VFS/ for IO interception, and Source/Tools/IOWrapper/ integrates with Source/Runtime/VFS/ for distributed build file system wrapping. All 24 top-level modules (8 Runtime + 2 Extensions + 6 ContentPipeline + 2 Tools + 6 Programs) are accessible from Source/ with real path references under Source/.
