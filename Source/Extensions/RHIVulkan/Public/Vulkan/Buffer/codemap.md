# Source/Extensions/RHIVulkan/Public/Vulkan/Buffer/

The Buffer folder manages Vulkan buffer creation, allocation, and lifecycle. This is a core subsystem used by the frame graph, pipelines, and command recording to store vertex data, index data, uniform buffers, and storage buffers on the GPU.

## Responsibility
This folder owns Vulkan buffer creation, allocation, and lifecycle management. It provides type-safe buffer objects that encapsulate VkBuffer and associated VkMemoryRequirements, with automatic memory allocation via the HAL memory pools. The folder handles vertex buffers, index buffers, uniform buffers, storage buffers, and staging buffers. It provides type-safe access to buffer data via Get<T>() methods and manages buffer lifecycle from creation to destruction. The design is focused on minimizing CPU overhead while providing safe, RAII-style buffer management.

## Design
Buffer management is centered on FVulkanBuffer, which encapsulates a VkBuffer and its associated memory. FVulkanBuffer provides constructors that take a size, usage flags, and property flags, and automatically allocates memory via the HAL's TMemoryPool or TSlabHeap. FVulkanStagingBuffer is a specialized buffer for CPU-to-GPU data transfers, mapped and written on the CPU side and flushed to GPU via command buffers. TVulkanBufferRef is a smart pointer type that tracks buffer lifetime and prevents premature destruction. The buffer design supports dynamic buffering via FVulkanBufferManager, which can reallocate buffers when sizes change. Memory allocation uses TMemoryPool for large, persistent buffers and TSlabHeap for small, frequently allocated buffers. Key type names include FVulkanBuffer, FVulkanStagingBuffer, TVulkanBufferRef, and FVulkanBufferManager.

## Flow
The buffer flow begins with buffer creation via FVulkanBuffer::Create(), which specifies size, usage (vertex, index, uniform, storage), and property flags (host visible, host coherent, device local). The buffer object allocates memory via the HAL's memory pool, mapping the VkMemoryAllocateInfo to the appropriate pool. Data can be written via Map() and Unmap() for host-visible buffers, or via staging buffers for device-local buffers. For staging, CPU data is written to a FVulkanStagingBuffer, which is then submitted as a copy command to transfer data to the target device-local buffer. Buffer destruction goes through FVulkanBufferManager or reference counting via TVulkanBufferRef, which ensures the buffer is not destroyed while in use by the command graph. Buffers are consumed by FVulkanPipelineResources for descriptor set binding, by FVulkanCommandBuffer for vertex/index data, and by the frame graph for uniform and storage buffers.

## Integration
Buffer management integrates with FVulkanDevice (HAL) for creation and destruction, with TMemoryPool and TSlabHeap (HAL) for memory allocation, and with FVulkanPipelineResources for descriptor set binding. Vertex and index buffers are consumed by FVulkanCommandBuffer for command recording. Uniform and storage buffers are consumed by the frame graph (FVulkanFrameGraph) for shader resources. Staging buffers integrate with the command submission system for CPU-to-GPU transfers. TVulkanBufferRef is consumed by any code that needs to track buffer lifetime across frames. The buffer system is also integrated with Source/Runtime/Core/Public/Memory/ for fallback memory allocation when HAL pools are unavailable.
