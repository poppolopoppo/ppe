# Source/Tools/

## Responsibility
Source/Tools/ aggregates developer utilities and system integration tools for the PPE engine. This folder contains 2 primary modules: IODetouring and IOWrapper. IODetouring provides Win32 IO interception via MinHook/Detours for debugging, profiling, and file system monitoring. IOWrapper provides file system wrapping for distributed builds, enabling file operation redirection and tracking across build nodes. These tools support engine development, debugging, and distributed build workflows by integrating with the runtime VFS, serialization, and modular services systems. The Tools/ folder is essential for diagnosing IO-related issues, implementing distributed build strategies, and providing developer-facing utilities that interact with the engine's core systems.

## Design
Source/Tools/ follows a specialized design focused on file system interception and distribution. IODetouring/ implements Win32 IO interception using MinHook or Detours libraries, allowing hooking of ReadFile, WriteFile, CreateFile, and other Win32 API functions for monitoring and modifying file operations at the platform level. It integrates with Source/Runtime/VFS/ to intercept virtual file system operations and with Source/Runtime/Serialize/ for serialization debugging. The module uses platform-specific macros and conditional compilation (conditional on USE_PPE_VIRTUALLOC_DETOUR=1 define and External/minhook PrivateDependency). IOWrapper/ provides file system wrapping capabilities for distributed builds, redirecting file operations to remote or cached locations. It uses Source/Runtime/VFS/ mount point infrastructure and FFileSystemTrie for path resolution. Both modules follow the standard module lifecycle and register via `*-module.json` with the build system. IODetouring/ has PrivateDependencies on External/minhook and External/vstools (for Windows SDK functions), while IOWrapper/ integrates with the modular services registry and depends on Source/Runtime/VFS/ for mount point resolution.

## Flow
Source/Tools/ tools integrate into the engine workflow through hook points and redirection layers. IODetouring/ hooks Win32 API calls early in process startup, intercepting all file operations that then flow through the interception layer. When active, every ReadFile/WriteFile/CreateFile call passes through the detour, where it can be logged, redirected, or modified before being forwarded to the original API. Intercepted operations can write to log files, track allocation patterns, or redirect to alternative paths — useful for debugging serialization issues, analyzing asset access patterns, or implementing custom file virtualization. The hooked operations then proceed to the actual Win32 implementation or, if redirected, to an alternative destination. IOWrapper/ intercepts file operations at the VFS level, redirecting them through the virtual file system mount infrastructure. When a program requests file access, the request flows through IOWrapper/ which can redirect to a distributed build cache, a network location, or a local cache based on the build configuration. Both tools participate in the module lifecycle (Start → PostStart → DutyCycle → PreShutdown → Shutdown) and register their services via FModularServices, making them available to other modules that need file system inspection or redirection capabilities.

## Integration
Source/Tools/ integrates closely with Source/Runtime/VFS/ as its primary dependency. IODetouring/ hooks into VFS operations, intercepting Readable/Writable/ReadWritable operations and providing a debugging window into the virtual file system's behavior. It also connects to Source/Runtime/Serialize/ for serialization-related IO debugging — detecting when assets are read/written during load/save operations. IOWrapper/ is built on top of VFS/ mount points, redirecting file operations through the trie-based path resolution system. It supports distributed build workflows by forwarding file requests to remote locations while maintaining transparency for the requesting program. Both tools are referenced by Source/Programs/ — IOWrapperTest/ specifically tests IOWrapper/ functionality, and BuildRobot/ may use IODetouring/ for asset access pattern analysis. Source/Extensions/ApplicationUI/ may use IODetouring/ for debugging ImGui resource loading. The integration path flows: Program → IOWrapperTest/ → IOWrapper/ → VFS/ → Runtime modules, and: Program with IODetouring enabled → IODetouring/ → Win32 API → VFS/ → Runtime modules. Both Tools/ modules also integrate with the modular services system, registering themselves as available services for other modules to discover and use.
