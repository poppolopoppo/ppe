# Source/Runtime/Serialize/Public/Text/

The Text serializer folder implements the DSL (Domain Specific Language) script format (.txt/.script) for engine object (de)serialization. FTextSerializer implements the ISerializer interface and uses the Lexer/Parser pipeline to convert script source into AST nodes, evaluate the AST via FParseContext to produce FAtom results, and populate FMetaObject instances. The Text format is the only format that uses the full DSL pipeline (Lexer → Parser → AST → FParseContext → FAtom → FMetaObject), making it suitable for script-driven content, level description, and any scenario where a custom language for object configuration is desired. The Grammar.h file defines the grammar startup symbols and initializes the parser/lexer singletons. This format supports round-trip conversion: script source → AST → object graph and back, driven by the RTTI reflection system. The Text format is the most expressive of the supported formats, as it allows custom syntax, control flow, and complex object graphs described in a script-like language.

## Responsibility

This folder owns the Text/DSL script format serializer that provides script-based (de)serialization of engine objects using the full Lexer/Parser pipeline. FTextSerializer implements ISerializer::Deserialize() and ISerializer::Serialize(), delegating to the Lexer for tokenization, the Parser for AST construction, and FParseContext for evaluation. The DSL grammar defines the language constructs available in the script: variable export/binding, object definitions with property statements, arithmetic and logical expressions, function calls via RTTI, and literal values. The round-trip path is: script source → FLexer → FMatch tokens → Parser → AST (FParseExpression/FParseStatement) → FParseContext evaluation → FAtom results → FMetaObject property population. The Grammar.h file initializes the parser/lexer singletons with the grammar symbols. This format is commonly used for script-driven content, level description, AI behavior configurations, and any scenario where a custom language for object configuration is desired.

## Design

The design of the Text/DSL format centers on the full parser pipeline as the (de)serialization mechanism. The ISerializer interface is implemented by FTextSerializer, which chains: FLexer tokenizes the input stream → produces FMatch tokens → Parser recursive-descent → AST of FParseExpression/FParseStatement nodes → FParseContext evaluates AST with SLABHEAP(Atom) temporary allocations → FAtom results → FMetaObject property population via RTTI. The grammar is defined at startup via FGrammarStartup, which initializes the FLexer and Parser with all keywords, operators, typenames, and literal types. The parser AST nodes are extensive: TLiteral<T> for literals, FVariableExport for export/public/private binding, FVariableReference for $path references, TUnaryFunction/TBinaryFunction for operators, TTernary for conditionals, FObjectDefinition for object literals, FPropertyReference for obj.property, FTupleExpr/FArrayExpr/FDictionaryExpr for collections, FCastExpr for casts, FFunctionCall for RTTI-driven function calls, FSubscriptOperator for obj[index]. The FParseContext provides the evaluation infrastructure: a scope object (RTTI object) for variable resolution, local/global variable maps, and SLABHEAP(Atom) for temporary allocations. The format is designed to be extensible: new grammar rules can be added without changing the core serializer, and custom functions can be registered via FMetaFunction.

## Flow

Data flow for Text/DSL format: User code calls FTextSerializer.Serialize(ctx, output) or FTextSerializer.Deserialize(ctx, input). Save path: FTextSerializer → BuildTransaction(ctx, sources) → FetchSources() → filenames → FLexer tokenizes each source → Parser produces AST → FParseContext evaluates AST → FAtom results → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Serialize() → output stream. Load path: FTextSerializer → BuildTransaction → same parser pipeline → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Deserialize() → object graph. The parser AST nodes flow from TLiteral/TBinaryFunction/FCastExpr/FFunctionCall at the expression level through FObjectDefinition/FPropertyStatement at the statement level. FParseContext::Eval() walks the AST: for TLiteral<T>, the value is directly produced as an FAtom; for FVariableReference, the lookup occurs in the scope object's local/global maps; for FFunctionCall, FMetaFunction::Invoke() is called via RTTI; for FPropertyReference, FMetaProperty::Get() reads the property. The result FAtom carries type-erased data that populates the FMetaObject. Transaction lifecycle: FTransactionSerializer.Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded. The Grammar.h startup initializes the lexer/parser with all DSL symbols.
