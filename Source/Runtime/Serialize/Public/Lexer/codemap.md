# Source/Runtime/Serialize/Public/Lexer/

The Lexer folder implements the tokenizer that powers the DSL (Domain Specific Language) parser for the Text/Script format. The FLexer class reads an input stream and produces a sequence of FMatch tokens, each containing a symbol, span (source location), and value. The lexer is the first stage in the serialization pipeline for the Text format: FLexer → FMatch → Parser → AST → FParseContext → FAtom → FMetaObject. The Private Lexer implementation (Lexer.cpp, Symbol.cpp, Symbols.cpp, LookAheadReader.cpp, Match.cpp, LookAheadReader.cpp) provides the concrete tokenization logic, including the global symbol table (FSymbols singleton) that defines all keywords, operators, punctuation, and typenames the lexer recognizes. The lexer also produces Location.h span information for error reporting and source position tracking. This folder is the entry point for any code that needs to tokenize a script source file for subsequent parsing by the Parser.

## Responsibility

This folder owns the tokenizer component that converts raw script source text into a structured token stream for the DSL parser. FLexer reads an input stream character by character, recognizing keywords, operators, punctuation, typenames, literals, and whitespace, and produces FMatch tokens that bundle a symbol descriptor (FSymbol*), a source code span (FSpan, from Location.h), and a value (which could be a string, number, or boolean). The global symbol table (FSymbols singleton) defines all recognized symbols: keywords like `export`, `public`, `private`, operators like `+`, `-`, `*`, `/`, `==`, `&&`, `!`, punctuation like `(`, `)`, `{`, `}`, `;`, `,`, and typenames that map to FMetaClass lookups. The lexer uses a lookahead pattern (LookAheadReader) to peek ahead in the input stream without consuming characters, enabling correct parsing of multi-character operators and typenames. The lexer also handles comments, string literals, and number parsing. The token stream is consumed by the recursive-descent Parser in Source/Runtime/Serialize/Public/Parser/.

## Design

The design of the lexer centers on the FMatch token as the unit of communication between lexer and parser, and the FSymbols singleton as the global registry of all recognized symbols. Each FMatch contains: a symbol (FSymbol* pointing into the FSymbols table), a span (FSpan from Location.h marking the start and end positions in the source text), and a value (a variant holding string literals, numeric values, or boolean flags). The FSymbols singleton is initialized at startup via FGrammarStartup and contains entries for all DSL keywords (`export`, `public`, `private`, `return`, etc.), operators (`+`, `-`, `*`, `/`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `&&`, `||`, `!`, `=`, `,`, `(`, `)`, `{`, `}`, `[`, `]`, `;`), punctuation, and typenames that resolve to FMetaClass names. The lookahead reader (LookAheadReader) enables the lexer to determine the correct token without consuming input prematurely, which is critical for parsing ambiguous constructs like `->` vs `- >` or `>=` vs `>`. The lexer is designed to be fast and low-overhead, as it is called once per source file load, and its output is the sole input to the parser.

## Flow

Data flow for lexing: Client code creates an FLexer with an input stream (typically a string or file stream) and calls NextToken() repeatedly until a "end of input" or error token is returned. Each call to NextToken() produces an FMatch containing: the recognized symbol (from FSymbols), the source code span (start line/column, end line/column), and the token value. The lexer maintains internal state: the current position in the input stream, whether we're inside a string literal or comment, and the lookahead buffer. The lexer skips whitespace (except within strings), handles escape sequences in strings, and recognizes number literals (integer, float) and boolean literals (`true`, `false`). When the input is exhausted, NextToken() returns a match with symbol set to a special "end of input" or "error" symbol. The FMatch tokens are then consumed by the Parser (Source/Runtime/Serialize/Public/Parser/) in a recursive-descent parsing loop. The lexer also produces Location.h span information that the parser uses for error reporting and source position tracking.

## Integration

This folder integrates with adjacent modules via real paths under Source/. Downstream: Source/Runtime/Serialize/Public/Parser/ where the FMatch token stream is consumed by the recursive-descent parser; Source/Runtime/Serialize/Private/Lexer/ where the concrete tokenizer implementation (Lexer.cpp, Symbol.cpp, etc.) lives; Source/Runtime/Serialize/Public/ where the lexer is part of the public DSL infrastructure; Source/Runtime/RTTI/ where typenames in the DSL source resolve to FMetaClass lookups during parser evaluation; Source/Runtime/Serialize/Public/Text/ where the Text format uses the lexer as its entry point. Specific paths: Source/Runtime/Serialize/Public/Lexer/Lexer.h, Source/Runtime/Serialize/Public/Lexer/Symbol.h, Source/Runtime/Serialize/Public/Lexer/LookAheadReader.h, Source/Runtime/Serialize/Private/Lexer/Lexer.cpp, Source/Runtime/Serialize/Private/Lexer/Symbol.cpp, Source/Runtime/Serialize/Private/Lexer/LookAheadReader.cpp, (for typename resolution), Source/Runtime/Serialize/Public/Parser/ParseContext.h (for atom heap used during evaluation). The lexer also integrates with Source/Runtime/Serialize/Public/Text/Grammar.h for grammar startup initialization.
