# Source/Runtime/Serialize/Public/

The Public Serialize folder contains the format-specific serializer implementations and the DSL infrastructure (Lexer, Parser, Grammar) that powers the Text/Script format. Five format serializers live here: FBinarySerializer (binary/.bin, compact schema-less), FJsonSerializer (JSON/.json, human-readable with RTTI helpers), FTextSerializer (DSL script/.txt/.script, uses parser pipeline), FFATSerializer (FAT/.fat, indexed multi-object container), and FMarkupSerializer (XML/Markup/.xml, fragment-based with minify). The DSL infrastructure consists of the Lexer (tokenizer producing FMatch tokens), Parser (recursive-descent AST builder), and Grammar (grammar definitions for the script language). The ISerializer abstract interface is defined in Source/Runtime/Serialize/Public/ISerializer.h, and all format serializers inherit or implement it. The Transaction system headers (FTransactionSerializer, FTransactionSaver, FTransactionLinker) are also in the Public folder, providing the unit-of-work and cross-reference resolution layer. This folder is intentionally the public-facing surface for all serialization formats — any external module or tool that needs to (de)serialize engine objects will #include headers from this folder.

## Responsibility

This folder owns the public-facing serialization format implementations that external modules and tools use to convert engine objects to persistent formats. FBinarySerializer handles compact binary (.bin) format with schema-less encoding, suitable for fast load/store operations. FJsonSerializer handles JSON (.json) format with RTTI_to_Json and Json_to_RTTI helpers for round-trip conversion via FMetaObject/FMetaProperty. FTextSerializer handles the DSL script format (.txt/.script) using the Lexer/Parser pipeline for round-trip deserialization through the AST and RTTI metadata. FFATSerializer handles the FAT format (.fat) with index-based random access for multi-object containers. FMarkupSerializer handles XML/Markup (.xml) format with fragment-based parsing and minify options. The ISerializer abstract interface (Deserialize/Serialize) is the contract all these implement. The transaction system headers (FTransactionSerializer, FTransactionSaver, FTransactionLinker) provide the unit-of-work and cross-reference resolution layer that sits above the format serializers. All format serializers depend on the RTTI system (FMetaObject, FMetaProperty, FAtom) for type-aware (de)serialization.

## Design

The design separates format-specific serialization logic from the transaction orchestration layer. Each format serializer implements ISerializer in a format-appropriate way: FBinarySerializer uses compact binary encoding with no schema requirement, FJsonSerializer uses human-readable JSON with explicit RTTI helper functions for round-trip conversion, FTextSerializer delegates to the Lexer/Parser DSL pipeline for script-based deserialization, FFATSerializer uses the FAT index format for random-access multi-object containers, and FMarkupSerializer uses fragment-based XML parsing with an optional minify pass. The Lexer tokenizes input into FMatch (symbol + span + value) tokens, the Parser performs recursive-descent parsing into an AST of FParseExpression/FParseStatement nodes, and the Grammar defines the language grammar for the script format. The Parser AST nodes include TLiteral<T> for literals, FVariableExport for variable binding, FVariableReference for $path references, TUnaryFunction/TBinaryFunction for operators, FObjectDefinition for object literals, FPropertyReference for obj.property, FTupleExpr/FArrayExpr/FDictionaryExpr for collection literals, FCastExpr for explicit casts, FFunctionCall for RTTI-driven function calls, and FSubscriptOperator for obj[index]. The transaction system (FTransactionSerializer, FTransactionSaver, FTransactionLinker) adds a layer on top: BuildTransaction → Parse → Link → Save/Load, where FTransactionLinker.Resolve() fixes cross-references using FMetaDatabase lookups.

## Flow

Serialization flow for each format: User code creates an FTransactionSerializer (or directly uses a format serializer) and calls SaveTransaction(ctx, output) or LoadTransaction(ctx, input). Save path: BuildTransaction(ctx, sources) → FetchSources() → filenames → FLexer tokenizes each source → Parser produces AST → FParseContext evaluates AST → FAtom results → FTransactionLinker.Resolve() → FMetaTransaction (loaded refs) → ISerializer.Serialize() → output stream. Load path: BuildTransaction(ctx, sources) → same parser pipeline → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Deserialize() → object graph. For the Text/DSL format specifically: FLexer tokenizes the input stream → produces FMatch tokens → Parser recursive-descent → AST (FParseExpression/FParseStatement) → FParseContext with SLABHEAP(Atom) temporary allocations → FAtom results → FMetaObject property population via RTTI → object graph construction. The Parser AST nodes flow from TLiteral/TBinaryFunction/FCastExpr/FFunctionCall at the expression level through FObjectDefinition/FPropertyStatement at the statement level. Transaction lifecycle: FTransactionSerializer.Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded, with FLinearizedTransaction resolving cross-references.

## Integration

This folder integrates with adjacent modules via real paths under Source/. Downstream consumers: Source/Runtime/RTTI/ where all format serializers depend on FMetaObject/FMetaProperty/FAtom for type-aware (de)serialization; Source/Runtime/Serialize/Private/ where the concrete implementation details (BinaryFormat.h, JsonSerializer.cpp, etc.) live; Source/Runtime/VFS/ where FTransactionSerializer reads source files via FVirtualFileSystem::ReadAll/Glob; Source/Runtime/Network/ and Source/Runtime/Remoting/ where serialized data can be carried in HTTP responses (JSON via FJsonSerializer, binary via FBinarySerializer); Source/Runtime/Application/ where user code invokes the format serializers. Specific paths: , Source/Runtime/Serialize/Private/Binary/BinaryFormat.h, Source/Runtime/Serialize/Public/Json/JsonSerializer.h, Source/Runtime/Serialize/Private/Lexer/Lexer.cpp, Source/Runtime/Serialize/Public/Parser/ParseContext.h. The transaction system also integrates with Source/Runtime/Serialize/Private/TransactionLinker.cpp for import resolution.
