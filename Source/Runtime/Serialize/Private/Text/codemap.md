# Source/Runtime/Serialize/Private/Text/

The Private Text folder implements the concrete Text/DSL script serializer that powers the public FTextSerializer. TextSerializer.cpp provides the actual serializer logic, delegating to the Lexer for tokenization, the Parser for AST construction, and FParseContext for evaluation. The Private folder is the implementation detail that makes the public FTextSerializer work — external systems should not need to include headers from this folder, as the Public folder's FTextSerializer.h provides the stable API surface. The Text format is the only format that uses the full DSL pipeline (Lexer → Parser → AST → FParseContext → FAtom → FMetaObject), making it suitable for script-driven content, level description, and any scenario where a custom language for object configuration is desired. The Grammar.h file defines the grammar startup symbols and initializes the parser/lexer singletons. This format supports round-trip conversion: script source → AST → object graph and back, driven by the RTTI reflection system.

## Responsibility

This folder owns the concrete Text/DSL script serialization implementation that powers the public FTextSerializer. TextSerializer.cpp implements the actual serializer logic, delegating to the Lexer for tokenization (FLexer → FMatch tokens), the Parser for AST construction (recursive-descent → FParseExpression/FParseStatement nodes), and FParseContext for evaluation (SLABHEAP(Atom) temporary allocations → FAtom results). The round-trip path is: script source → FLexer → FMatch tokens → Parser → AST → FParseContext evaluation → FAtom results → FMetaObject property population. The Grammar.h file initializes the parser/lexer singletons with all DSL symbols. The format supports round-trip conversion and is commonly used for script-driven content, level description, AI behavior configurations, and any scenario where a custom language for object configuration is desired.

## Design

The design of the Text/DSL serializer implementation centers on the full parser pipeline as the (de)serialization mechanism. FTextSerializer uses the ISerializer interface and chains: FLexer tokenizes the input stream → produces FMatch tokens → Parser recursive-descent → AST of FParseExpression/FParseStatement nodes → FParseContext evaluates AST with SLABHEAP(Atom) temporary allocations → FAtom results → FMetaObject property population via RTTI. The grammar is defined at startup via FGrammarStartup, which initializes the FLexer and Parser with all keywords, operators, typenames, and literal types. The parser AST nodes are extensive: TLiteral<T> for literals, FVariableExport for export/public/private binding, FVariableReference for $path references, TUnaryFunction/TBinaryFunction for operators, TTernary for conditionals, FObjectDefinition for object literals, FPropertyReference for obj.property, FTupleExpr/FArrayExpr/FDictionaryExpr for collections, FCastExpr for casts, FFunctionCall for RTTI-driven function calls, FSubscriptOperator for obj[index]. The FParseContext provides the evaluation infrastructure: a scope object (RTTI object) for variable resolution, local/global variable maps, and SLABHEAP(Atom) for temporary allocations. The format is designed to be extensible: new grammar rules can be added without changing the core serializer, and custom functions can be registered via FMetaFunction.

## Flow

Data flow for Text/DSL format: User code calls FTextSerializer.Serialize(ctx, output) or FTextSerializer.Deserialize(ctx, input). Save path: FTextSerializer → BuildTransaction(ctx, sources) → FetchSources() → filenames → FLexer tokenizes each source → Parser produces AST → FParseContext evaluates AST → FAtom results → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Serialize() → output stream. Load path: FTextSerializer → BuildTransaction → same parser pipeline → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Deserialize() → object graph. The parser AST nodes flow from TLiteral/TBinaryFunction/FCastExpr/FFunctionCall at the expression level through FObjectDefinition/FPropertyStatement at the statement level. FParseContext::Eval() walks the AST: for TLiteral<T>, the value is directly produced as an FAtom; for FVariableReference, the lookup occurs in the scope object's local/global maps; for FFunctionCall, FMetaFunction::Invoke() is called via RTTI; for FPropertyReference, FMetaProperty::Get() reads the property. The result FAtom carries type-erased data that populates the FMetaObject. Transaction lifecycle: FTransactionSerializer.Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded. The Grammar.h startup initializes the lexer/parser with all DSL symbols.

## Integration

This folder integrates with adjacent modules via real paths under Source/. Downstream consumers: Source/Runtime/RTTI/ where FTextSerializer depends on FMetaObject/FMetaProperty/FAtom for type-aware property traversal and RTTI-driven function calls; Source/Runtime/Serialize/Private/Lexer/ and Source/Runtime/Serialize/Private/Parser/ where the concrete lexer and parser implementations live; Source/Runtime/Serialize/Public/Lexer/ and Source/Runtime/Serialize/Public/Parser/ where the public lexer and parser APIs are defined; Source/Runtime/Serialize/Public/Text/ where FTextSerializer.h provides the public API; Source/Runtime/Serialize/Public/Text/Grammar.h where grammar symbols are initialized; where the grammar symbols are registered at startup. Specific paths: Source/Runtime/Serialize/Private/Text/TextSerializer.cpp, Source/Runtime/Serialize/Public/Lexer/Lexer.h, Source/Runtime/Serialize/Public/Parser/ParseContext.h, Source/Runtime/Serialize/Private/Lexer/Lexer.cpp, Source/Runtime/Serialize/Private/Parser/ParseExpression.cpp, Source/Runtime/Serialize/Public/Text/Grammar.h. The Text format is also the primary consumer of the Parser's AST evaluation and the Lexer's token stream.
