# Source/Runtime/Serialize/Private/Parser/

The Private Parser folder implements the concrete recursive-descent parser that powers the DSL for the Text/Script format. ParseExpression.cpp, ParseContext.cpp, and the other .cpp files provide the actual parsing logic, AST construction, and evaluation infrastructure that powers the Text format's (de)serialization. The parser consumes FMatch tokens from the Lexer and builds an abstract syntax tree (AST) of FParseExpression and FParseStatement nodes, which are then evaluated by FParseContext to produce FAtom results that populate FMetaObject instances. This folder is the implementation detail that makes the public Parser work — external systems should not need to include headers from this folder, as the Public folder's Parser.h provides the stable API surface. The parser AST nodes include: TLiteral<T> for literal values (int, float, string, bool, null), FVariableExport for export/public/private variable binding, FVariableReference for $path.to.variable references, TUnaryFunction<T> for unary operators (-x, !x, etc.), TBinaryFunction<T> for binary operators (+, -, *, /, ==, &&, ||, etc.), TTernary<Test> for ternary conditional (cond ? true : false), FObjectDefinition for object literals with property statements, FPropertyReference for obj.property access, FTupleExpr for tuple literals (a, b, c), FArrayExpr for array literals [a, b, c], FDictionaryExpr for dictionary literals {key: value...}, FCastExpr for explicit (Type)expr casts, FFunctionCall for obj.func(args...) via RTTI, and FSubscriptOperator for obj[index] with multi-type support. The parser also produces a FParseContext with a SLABHEAP(Atom) temporary allocation arena for evaluation, and FParseResult objects for error cases.

## Responsibility

This folder owns the concrete parser implementation that converts the FMatch token stream from the Lexer into an abstract syntax tree (AST) representing the DSL script's structure and semantics. The .cpp files here (ParseExpression.cpp, ParseContext.cpp, ParseStatement.cpp, ParseList.cpp, ParseItem.cpp, Parser.cpp) implement the recursive-descent parsing methods that build the AST node by node. ParseExpression.cpp handles all expression rules: primary expressions (literals, subscripts, casts), unary operators, binary operators, and ternary operators, respecting precedence through method nesting. ParseContext.cpp provides the evaluation infrastructure: a SLABHEAP(Atom) temporary allocation arena for FAtom results, a scope object (RTTI object) for variable resolution, and local/global variable maps. ParseStatement.cpp handles statement rules: variable export, object definitions, property statements, and function calls. The parser also handles error recovery by consuming tokens until a synchronizing token is found and producing a failed FParseResult with position information. The AST nodes are ref-counted via PCParseExpression = TRefPtr<FParseExpression>.

## Design

The design of the parser implementation centers on the recursive-descent pattern with a shared FParseContext that provides the evaluation infrastructure. Each .cpp file implements a set of parsing methods that know how to parse their construct from the token stream. The parser respects operator precedence through the nesting of parsing methods: primary expressions (literals, subscripts, casts) are parsed at the lowest level, unary operators at the next level, binary operators at the next, and ternary at the top. This nesting ensures that `a + b * c` is parsed correctly without explicit precedence declarations. The FParseContext provides the evaluation infrastructure: a SLABHEAP(Atom) temporary allocation arena for FAtom results, a scope object (RTTI object) for variable resolution, and local/global variable maps. The parser also produces FParseItem nodes that carry source location (FSpan from Location.h) for error reporting. The AST nodes are designed for extensibility: new grammar rules can be added by adding new AST node subclasses and parsing methods, without changing the core parsing infrastructure. The implementation is in the .cpp files, while the .h files in the Public folder declare the interfaces and forward declarations.

## Flow

Data flow for parsing: FLexer produces a sequence of FMatch tokens → Parser .cpp recursive-descent methods consume tokens and build AST → AST of FParseExpression/FParseStatement nodes → FParseContext evaluates AST → FAtom results are produced → FMetaObject property population via RTTI. The parsing flow begins when the parser is initialized with a token stream from the lexer. It then parses a complete script source unit (typically starting with a top-level expression or statement). The recursive-descent methods consume tokens one at a time, creating AST nodes as they go. Precedence is handled by method nesting: primary parsing → unary → binary → ternary. After the AST is fully built, FParseContext::Eval() is called, which walks the AST, evaluating each node. For TLiteral<T>, the value is directly produced as an FAtom. For FVariableReference, the parser looks up the variable in the scope object's local/global maps. For FFunctionCall, the parser invokes FMetaFunction::Invoke() via RTTI. For FPropertyReference, the parser reads the property via FMetaProperty::Get(). The result is an FAtom that carries type-erased data, which can then be used by the serializer or stored in an FMetaObject. The parser also produces FParseResult objects for error cases, including the position (line, column) where the error occurred. The flow is: token stream → recursive-descent parsing → AST construction → FParseContext evaluation → FAtom output.
