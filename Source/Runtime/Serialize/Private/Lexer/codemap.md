# Source/Runtime/Serialize/Private/Lexer/

The Private Lexer folder implements the concrete tokenizer that powers the DSL parser for the Text/Script format. Lexer.cpp provides the actual tokenization logic, including the global symbol table (FSymbols singleton) management, token production, and input stream handling. The Private Lexer implementation (Lexer.cpp, Symbol.cpp, Symbols.cpp, LookAheadReader.cpp, Match.cpp, LookAheadReader.cpp) provides the concrete tokenization logic, including the global symbol table (FSymbols singleton) that defines all keywords, operators, punctuation, and typenames the lexer recognizes. The lexer is the first stage in the serialization pipeline for the Text format: FLexer → FMatch → Parser → AST → FParseContext → FAtom → FMetaObject. This folder is the implementation detail that makes the public FLexer work — external systems should not need to include headers from this folder, as the Public folder's Lexer.h provides the stable API surface.

## Responsibility

This folder owns the concrete tokenizer implementation that converts raw script source text into FMatch tokens. Lexer.cpp implements the actual tokenization logic: reading the input stream character by character, recognizing keywords, operators, punctuation, typenames, literals, and whitespace, and producing FMatch tokens that bundle a symbol (FSymbol* pointing into the FSymbols table), a source code span (FSpan from Location.h), and a value (string, number, or boolean). The global symbol table (FSymbols singleton) is managed here and defines all recognized symbols: keywords like `export`, `public`, `private`, operators like `+`, `-`, `*`, `/`, `==`, `&&`, `!`, punctuation like `(`, `)`, `{`, `}`, `;`, `,`, and typenames that map to FMetaClass lookups. The lookahead pattern (LookAheadReader) is implemented here to peek ahead in the input stream without consuming characters, enabling correct parsing of multi-character operators and typenames. The lexer also handles comments, string literals, and number parsing. The token stream is consumed by the recursive-descent Parser in Source/Runtime/Serialize/Private/Parser/.

## Design

The design of the lexer implementation centers on the FMatch token as the unit of communication between lexer and parser, and the FSymbols singleton as the global registry of all recognized symbols. Each FMatch contains: a symbol (FSymbol* pointing into the FSymbols table), a span (FSpan from Location.h marking the start and end positions in the source text), and a value (a variant holding string literals, numeric values, or boolean flags). The FSymbols singleton is initialized at startup via FGrammarStartup and contains entries for all DSL keywords (`export`, `public`, `private`, `return`, etc.), operators (`+`, `-`, `*`, `/`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `&&`, `||`, `!`, `=`, `,`, `(`, `)`, `{`, `}`, `[`, `]`, `;`), punctuation, and typenames. The lookahead reader (LookAheadReader) enables the lexer to determine the correct token without consuming input prematurely, which is critical for parsing ambiguous constructs. The lexer is designed to be fast and low-overhead, as it is called once per source file load, and its output is the sole input to the parser. The implementation details are in Lexer.cpp, with symbol definitions in Symbol.cpp and Symbols.cpp, and the lookahead reader in LookAheadReader.cpp.

## Flow

Data flow for lexing: Client code creates an FLexer with an input stream (typically a string or file stream) and calls NextToken() repeatedly until a "end of input" or error token is returned. Each call to NextToken() produces an FMatch containing: the recognized symbol (from FSymbols), the source code span (start line/column, end line/column), and the token value. The lexer maintains internal state: the current position in the input stream, whether we're inside a string literal or comment, and the lookahead buffer. The lexer skips whitespace (except within strings), handles escape sequences in strings, and recognizes number literals (integer, float) and boolean literals (`true`, `false`). When the input is exhausted, NextToken() returns a match with symbol set to a special "end of input" or "error" symbol. The FMatch tokens are then consumed by the Parser (Source/Runtime/Serialize/Private/Parser/) in a recursive-descent parsing loop. The lexer also produces Location.h span information that the parser uses for error reporting and source position tracking. The flow is: input stream → lexer state machine → FMatch token → parser token stream.

## Integration

This folder integrates with adjacent modules via real paths under Source/. Downstream: Source/Runtime/Serialize/Public/Lexer/ where the public FLexer API is defined; Source/Runtime/Serialize/Private/Parser/ where the FMatch token stream is consumed by the parser; Source/Runtime/Serialize/Public/Parser/ where the parser consumes the token stream; Source/Runtime/RTTI/ where typenames in the DSL source resolve to FMetaClass lookups during parser evaluation; Source/Runtime/Serialize/Public/Text/ where the Text format uses the lexer as its entry point. Specific paths: Source/Runtime/Serialize/Private/Lexer/Lexer.cpp, Source/Runtime/Serialize/Private/Lexer/Symbol.cpp, Source/Runtime/Serialize/Private/Lexer/Symbols.cpp, Source/Runtime/Serialize/Private/Lexer/LookAheadReader.cpp, Source/Runtime/Serialize/Public/Lexer/Lexer.h, Source/Runtime/Serialize/Public/Lexer/Symbol.h, Source/Runtime/Serialize/Public/Lexer/LookAheadReader.h, (for typename resolution), Source/Runtime/Serialize/Public/Parser/ParseContext.h (for atom heap used during evaluation). The lexer also integrates with Source/Runtime/Serialize/Public/Text/Grammar.h for grammar startup initialization.
