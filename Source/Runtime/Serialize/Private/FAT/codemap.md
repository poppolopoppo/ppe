# Source/Runtime/Serialize/Private/FAT/

The Private FAT folder implements the low-level FAT format details that underlie the public FFATSerializer. FATFormat.h defines the exact index structure and object layout for the FAT (File Allocation Table) format, including the header with magic number, version, and object count, and the index table that maps object indices to file offsets and sizes. The FAT format is designed for scenarios where many objects need to be stored in a single file and individual objects need to be accessed without loading the entire file into memory. This folder is the implementation detail that makes the public FFATSerializer work — external systems should not need to include headers from this folder, as the Public folder's FFATSerializer.h provides the stable API surface. The format supports compression of individual object blocks, enables incremental load/mount cycles via the transaction system, and uses an index-based random-access approach for multi-object containers.

## Responsibility

This folder owns the concrete FAT format implementation that powers the public FFATSerializer. FATFormat.h defines the wire format structure: [4-byte magic number][4-byte version][4-byte object count][for each object: 4-byte offset][4-byte size], followed by the object data blocks at their respective file offsets. The index table enables random access to any object by its index without scanning the entire file. BinaryFormat.cpp in the Binary Private folder shares some of the same low-level binary details, as the FAT format builds upon the same schema-less binary encoding principles. The serializer reads the index first, then seeks to each object's offset and reads its size bytes, enabling efficient individual object access. The transaction system can wrap FAT operations for incremental mount/unmount cycles.

## Design

The design of the FAT format implementation centers on the index table as the key enabler of random access. The index table is a sorted array where each entry contains: [object_index → file_offset, object_size]. The index is built during serialization by writing each object's data and recording its file offset and size in the index. During deserialization, the index is read first, allowing any object to be loaded by seeking to the recorded offset and reading the recorded size. The format supports compression of individual object blocks (compressed vs uncompressed flag in the index entry). The transaction system can wrap FAT operations: FTransactionSerializer.BuildTransaction() → parse → FTransactionLinker.Resolve() → FATFormat read/write → MountToDB() for incremental loading. The format is designed to be extensible: new fields can be added to the header/index format without breaking compatibility, and objects can be versioned. The implementation is in FATFormat.h (declarations) and the associated .cpp files (not shown but implied by the .h design).

## Flow

Serialization flow for FAT: FFATSerializer (Public) → FATFormat.cpp → write header (magic, version, object count) → for each object: write data to file → record [offset, size] in index table → write index table at end of file. Load path: FATFormat.cpp → read header (magic, version, object count) → read index table (for each object, [offset, size]) → for each object, seek to offset → read size bytes → FMetaObject::RTTI_Load() → property population via FMetaProperty::Get() → FAtom type erasure. The transaction system can wrap this: FTransactionSerializer.LoadTransaction() → BuildTransaction → FTransactionLinker.Resolve() → FFATSerializer.Deserialize() → individual object loads with index random access. The format supports incremental mount: new objects can be added to an existing FAT file by appending data and updating the index, without re-writing the entire file. The flow is: index build → data write → index write → on load: index read → seek/read per-object → FMetaObject population.

## Integration

This folder integrates with the Public Serialize folder and the RTTI system via real paths under Source/. Downstream: where the public API is defined; Source/Runtime/RTTI/ where FMetaObject/FMetaProperty/FAtom provide type-aware property traversal; Source/Runtime/VFS/ where FAT file operations use FVirtualFileSystem::Read/Write at specific offsets; Source/Runtime/Serialize/Public/TransactionSerializer.h where the transaction system wraps FAT operations; Source/Runtime/Application/ where asset bundles and level data are packaged in FAT format. Specific paths: Source/Runtime/Serialize/Private/FAT/FATFormat.h, Source/Runtime/Serialize/Public/TransactionSerializer.h. The FAT format is also used as the underlying container format for the Binary serializer (see BinaryFormat.h).
