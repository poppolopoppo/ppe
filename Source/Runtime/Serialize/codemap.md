# Source/Runtime/Serialize/

The Serialize folder group owns all runtime data serialization and deserialization for the PPE engine. It is divided into Public and Private sub-folders, with Public containing the format-specific serializers (Binary, JSON, FAT, Markup, Text) and their associated DSL infrastructure (Lexer, Parser, Grammar), while Private implements the concrete serialization logic (BinaryFormat, JsonSerializer, TransactionLinker, etc.). The folder also houses the ISerializer abstract interface, the transaction system (FTransactionSerializer, FTransactionSaver, FTransactionLinker), and the format-specific detail headers. All serializers implement the ISerializer interface (Deserialize/Serialize methods) and depend on the RTTI reflection system (FMetaObject, FMetaProperty, FAtom) for type-aware (de)serialization. The transaction system provides a unit-of-work pattern (FMetaTransaction) that supports incremental load/mount cycles and cross-reference resolution during deserialization. This folder is the primary integration point between the engine's reflection system and its file/stream I/O subsystems.

## Responsibility

This folder owns all mechanisms for converting engine objects to and from various persistent formats. The Public sub-folder provides the format-specific serializers (FBinarySerializer for binary/.bin, FJsonSerializer for JSON/.json, FTextSerializer for the DSL script format/.txt, FFATSerializer for FAT/.fat, FMarkupSerializer for XML/Markup/.xml) that implement the ISerializer interface and handle format-level (de)serialization. The Private sub-folder implements the concrete serialization logic, format details, parser/tokenizer infrastructure, and the transaction system that provides unit-of-work semantics and cross-reference resolution. The ISerializer abstract interface defines Deserialize(ctx, input, linker) and Serialize(ctx, saver, output) as the contract all format serializers must fulfill. The transaction system (FTransactionSerializer, FTransactionSaver, FTransactionLinker) supports incremental load/mount cycles, import resolution, and linearized cross-reference fixing. The DSL parser (Lexer + Parser) enables the Text format to describe objects, properties, and values in a script-like language that can be round-tripped through the AST and RTTI metadata.

## Design

Key design decisions center on the ISerializer abstract interface, which separates format-specific logic (stream I/O, format parsing) from the transaction-level orchestration (FTransactionSerializer). Each format serializer (FBinarySerializer, FJsonSerializer, FTextSerializer, FFATSerializer, FMarkupSerializer) implements Deserialize and Serialize in format-appropriate ways: binary uses compact schema-less encoding, JSON uses human-readable key-value pairs with RTTI_to_Json/Json_to_RTTI helpers, Text uses the DSL parser/lexer pipeline, FAT uses an indexed multi-object container format, and Markup uses fragment-based XML parsing with minify options. The transaction system decouples parsing from object resolution: FTransactionSerializer.BuildTransaction() produces an AST via FLexer/Parser, FTransactionLinker.Resolve() fixes cross-references to FMetaObject instances, and FTransactionSaver provides a read-only view of loaded references. The DSL grammar (Lexer → Parser → AST → FParseContext → FAtom → FMetaObject) is the round-trip path for the Text format. FAT format uses FATFormat.h for its index-based random-access container. All format serializers depend on the RTTI system (FMetaObject, FMetaProperty, FAtom) for type-aware (de)serialization, but the RTTI system does not depend on any specific serializer.

## Flow

Data flow for serialization: User code calls FTransactionSerializer.SaveTransaction(ctx, sources) or FTransactionSerializer.LoadTransaction(ctx, sources). Save: FetchSources() → filenames → BuildTransaction(ctx, sources) → FLexer (tokenizer) → FMatch tokens → Parser (recursive descent) → AST (FParseExpression/FParseStatement) → FParseContext (evaluation with atom heap) → FAtom results → FTransactionLinker.Resolve() → FMetaTransaction (loaded refs) → ISerializer.Serialize() → output stream. Load: FetchSources() → BuildTransaction → same parser pipeline → FTransactionLinker.Resolve() → FMetaTransaction → ISerializer.Deserialize() → object graph. For the Text/DSL format specifically: FLexer tokenizes the input stream → produces FMatch (symbol + span) → Parser recursive-descent → AST nodes (FParseExpression, FParseStatement) → FParseContext with SLABHEAP(Atom) allocations → FAtom results → FMetaObject property population → RTTI-driven type resolution. Transaction flow: FTransactionSerializer.Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded, with FLinearizedTransaction flattening imported/loaded/exported refs for cross-reference resolution.

## Integration

This folder integrates with all other Runtime modules via real paths under Source/. Downstream consumers of serialized data: Source/Runtime/RTTI/ where all format serializers depend on FMetaObject/FMetaProperty/FAtom for type-aware (de)serialization; Source/Runtime/Network/ and Source/Runtime/Remoting/ where HTTP responses can carry serialized transactions (JSON via FJsonSerializer, binary via FBinarySerializer); Source/Runtime/VFS/ where FTransactionSerializer reads source files via FVirtualFileSystem::ReadAll/Glob; Source/Runtime/Application/ where user code invokes FTransactionSerializer for save/load operations. Specific paths: Source/Runtime/Serialize/Public/Binary/BinarySerializer.h, Source/Runtime/Serialize/Public/Json/JsonSerializer.h, Source/Runtime/Serialize/Public/Text/TextSerializer.h, Source/Runtime/Serialize/Public/Lexer/Lexer.h, Source/Runtime/Serialize/Public/Parser/Parser.h, Source/Runtime/VFS/Public/VirtualFileSystem.h, Source/Runtime/Remoting/Public/Remoting/RTTIEndpoint.h, Source/Runtime/Serialize/Private/Lexer/Lexer.cpp All modules ultimately depend on the ISerializer interface for save/load operations.
