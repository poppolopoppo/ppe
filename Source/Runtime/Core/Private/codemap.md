# Source/Runtime/Core/Private/

## Responsibility
This folder serves as the parent aggregator for all Private Core subsystems, containing implementation details, internal schedulers, lower-level utilities, and types not intended for external client code. It encompasses the private layers: Allocator, Container, Diagnostic, HAL (Windows, Linux, Generic), IO, Maths, Memory, Meta, and Time. The Private folder implements the Engine's internal machinery: the fiber-based task scheduler (FTaskScheduler, FTaskFiberPool), the memory allocation layer with leak detection integration, the compressed radix trie for block tracking, the platform-specific HAL implementations, and all internal data structures that support the Public API. Private folders are organized by function rather than exposure level, with each subfolder owning a specific domain of the Core subsystem's implementation.

## Design
The Private folder follows an implementation-first design where each subfolder provides the concrete machinery behind the Public API. The Thread/Task subsystem implements a work-stealing scheduler with FTaskQueued, per-worker priority heaps, and completion-port synchronization via FCompletionPort. The Allocator layer uses FMallocLowLevel with compile-time strategy selection (PPE_MALLOC_ALLOCATOR_STD, BINNED1, BINNED2, STOMP) and PageAllocator for virtual page caching with FCriticalSection-guarded free lists. The Diagnostics subsystem uses FBlockCompressedRadixTrie for leak tracking, FStackMarker for RAII-scoped profiling, and FIgnoreScope/FWhiteListScope for RAII-based suppression. The HAL Private subfolder implements platform-specific memory, atomics, threading, file I/O, and endianness with the same target-alias macro pattern as Public HAL but with internal implementation details. The Meta subfolder provides CRTP-based singletons (TSingleton, TAutoSingleton), type traits (Meta::TypeTraits), and compile-time utilities (TEnableIf, IF_CONSTEXPR). Memory management integrates FTrackingAllocator, FMemoryDomain, and FMemoryPool with thread-local caches under FPlatformAtomics. The Random generator uses XorShift+ variants (FXorShift64Star, FXorShift128Plus, FXorShift1024Star) seeded from process context.

## Flow
Private initialization flows from the modular system through internal subsystems: FTaskScheduler starts worker threads and fiber pools at module startup; FTrackingAllocator and FBlockTracker initialize leak detection metadata; FPlatformHAL resolves target platform and creates platform-specific instances; FMemoryPool and FMemoryDomain set up scoped memory arenas; FBasicBIHTree and random generators are seeded at startup; FIgnoreList and FIgnoreScope are registered as singletons. The main consumption loop: FTaskManager::Consume() pops tasks from worker queues, fibers execute their tasks and may post dependents, completion ports signal when tasks complete, leak tracking records allocations via FBlockHeader metadata, and diagnostic markers are pushed/popped around critical sections. Shutdown reverses this order: worker threads complete remaining tasks, leak detection generates final reports, profiler data is flushed, platform resources are cleaned up, and fiber pools are destroyed.

## Integration
The Private folder integrates with all Public subsystems and external Engine modules: Thread/ task scheduling feeds into Thread/ fiber execution and Thread Pool management; Allocator/ memory operations are the foundation for Container/ TVector/TArray, Memory/ smart pointers, and Maths/ types; Diagnostics/ FLeakDetector and FStackMarker are called by Memory/ allocation paths and Thread/ function entries; HAL/ Platform* implementations provide the OS-layer beneath all subsystems; Meta/ type traits and CRTP patterns are used across Memory/, Thread/, and Diagnostics/; IO/ deferred stream readers/writers integrate with Thread/ task pools for async file operations; Maths/ random generators are used by Task scheduler when USE_PPE_TASK_SCHEDULER_SHUFFLING is enabled and by rendering/post-processing pipelines; Container/ implementations rely on Allocator/ for all memory, and their types flow into Public APIs; Modular/ FModuleStaticRegistration and FModularServices use Private internal types for module interface reflection; and the root Public codemap.md references Private internals where they form the foundation of Public interfaces.
