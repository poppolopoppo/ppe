# Source/Runtime/Core/Private/Modular/

## Responsibility
The Modular folder owns the engine's plug-in module lifecycle, static/dynamic registration, phase-gated startup/shutdown, and dependency management. It implements FModularDomain as the central registry for all loaded modules, FModuleStaticRegistration for compile-time registered anchors, and FModuleDynamicRegistration for late-loaded shared libraries. The module system is phase-gated through EModulePhase (Bare, System, Framework, Application, User) and enforces usage flags (EModuleUsage) to selectively load or ignore modules based on their declared intent. Module duties (DutyCycle) allow periodic per-module work during the engine run loop.

## Design
The design centers on FModularDomain, which maintains _modules as a TUniquePtr-based map (FStringView → TUniquePtr<IModuleInterface>) keyed by module name, and _phaseStatus as a bitmask of active phases. Module registration is bifurcated: FModuleStaticRegistration::RegisterAnchor/FRegisterModule parse FModuleStaticAnchor function pointers and insert into a singleton registry protected by a read-write lock (WRITESCOPELOCK/_rwlock). FModuleDynamicRegistration::RegisterLibrary attaches a shared library path and anchor name, with lazy library AttachOrLoad on first access and reference-counted refcount tracking. LoadModuleIFP first checks the in-memory map, then falls back to static registration (FModuleStaticRegistration::Find), then dynamic registration (FModuleDynamicRegistration::Load), which may load a .dll/.so via Library.AttachOrLoad and resolve the anchor function. Each module's IModuleInterface provides Start/Shutdown/DutyCycle/PreShutdown/PostShutdown hooks called in phase order. The parent-child domain hierarchy (FModularDomain::_parent) enables nested module hierarchies, with ReleaseMemory propagating upward. EModulePhase gates enforce that modules can only start in their permitted phase or earlier, and StatusPhaseMask_/StatusStartPhase_/StatusShutdownPhase_ manage the bitmask transitions.

## Flow
The engine initialization flow calls FModularDomain::Start(domain), which pushes a splash screen, invokes _OnPreStart, then iterates GApplicationPhases_ (Bare → System → Framework → Application → User), calling StartPhase for each. StartPhase updates _phaseStatus, iterates all modules matching the current phase, and calls StartModule_ for each, which fires _OnPreModuleStart, mod.Start(*this), and _OnPostModuleStart. After all phases, PostStart is called on every module. The run loop calls DutyCycle() each frame, which iterates all modules in reverse order and calls their DutyCycle, then propagates to the parent domain if one exists. Shutdown reverses this flow: ShutdownPhase iterates phases in reverse (User → Bare), calls ShutdownModule_ (PreShutdown, mod.Shutdown, PostShutdown) for matching modules, then clears GAppDomainRef_. ReleaseMemory iterates modules in reverse and propagates upward to parents. Loading a module (LoadModuleIFP) checks the live map, static registry, then dynamic registry (which may load a library), loads the module initializer, validates name/phase, and emplaces the module into the domain. Unloading reverses this via UnloadModuleIFP, which erases from the map, calls FModuleDynamicRegistration::UnloadIFP to decrement refcount and possibly unload the library, and logs the event.

## Integration
Integration connects to Source/Runtime/Core/Private/Allocator/ (module initializer functions receive FAllocatorBlock for startup memory), Source/Runtime/Core/Private/Thread/ (module Start/Shutdown may create worker threads or fiber pools via the task scheduler), and Source/Runtime/Core/Private/Maths/ (random generators used for seed generation in module initialization). The modular system is the root of the dependency chain: See Source/Runtime/Core/Private/Allocator/ for allocation during module startup, Source/Runtime/Core/Private/Thread/ for task graph execution driven by module duty cycles, and Source/Runtime/Core/Private/Maths/ for RNG state passed through MakeSeed(). Downstream modules register via anchors in Source/Extensions/ or custom tooling; see Source/ for the public module registration API.
