# Source/Runtime/Core/Public/Modular/

## Responsibility
This folder implements the Engine's modular system: FModuleStaticRegistration, FModuleDynamicRegistration, FDynamicModule, IModuleInterface, FModuleInfo, FModuleEnums (EModulePhase, EModuleSource, EModuleUsage), FModularDomain, FModularServices, Modular_fwd.h, ModuleEnums.h, ModuleInfo.h, ModuleInterface.h, ModuleRegistration.h, and ModuleInterface.h. The folder provides the complete lifecycle management for Engine modules: static registration at link time, dynamic loading at runtime, service registration and lookup, and phase-based load ordering. FModularDomain drives the module load graph, determining load order via EModulePhase (PreEarly, Early, Normal, Late, PostLate). FModularServices provides a template-based service registry (RegisterService<Interface, Impl>, GetService<Interface>, UnregisterService<Interface>). FDynamicModule enables runtime-loaded plugins. IModuleInterface defines the pure virtual load/unload lifecycle. FModuleInfo carries module metadata (name, version, dependencies, phase). Module enums define source (Builtin, Plugin, Script) and usage (Required, Optional) classifications.

## Design
Modular design is phase-based and service-oriented. FModularDomain maintains an ordered list of FModuleStaticRegistration entries, resolved at startup into FDynamicModule instances via the module manifest. Load order is determined by EModulePhase: PreEarly modules load first (rendering core), followed by Early (systems), Normal (gameplay), Late (editors), PostLate (optional). FModularServices<Interface> uses a TMap<FName, TUniquePtr<IService>> for thread-safe service registration (RegisterService, GetService, UnregisterService). FDynamicModule::LoadModulePath(FName) dynamically FPlatformLoadLibrary the DLL/so, queries FModuleInterface::Initialize, and registers with FModularDomain. FModuleStaticRegistration holds the module name, FModuleInfo, and initialize function pointer; these are linked into the executable via the PPE_MODULE(...) macro. Module enums EModuleSource (Builtin, Plugin, Script) and EModuleUsage (Required, Optional) gate dependency resolution: Required modules must succeed; Optional modules may fail gracefully. IModuleInterface::Initialize() and Shutdown() are called by FModularDomain at the appropriate phase.

## Flow
Module startup: FModularDomain::Startup() iterates FModuleStaticRegistration list in phase order; each module's FModuleInterface::Initialize() is called; services are registered via FModularServices. Module dependency resolution: FModularDomain checks EModuleUsage(Required/Optional) and EModuleSource(Builtin/Plugin/Script) before loading. Service registration: caller invokes FModularServices::RegisterService<ISomeService>(ImplInstance); GetService<ISomeService>() returns the registered impl. Dynamic module load: FDynamicModule::LoadModulePath("PluginName") -> FPlatformLoadLibrary -> FModuleInterface::Initialize -> FModularDomain::Register. Module shutdown: reverse phase order; each module's Shutdown() called; services unregistered; DLL unloaded. Module info query: FModuleInfo::GetName(), GetPhase(), GetSource(), GetUsage() reflect module metadata. Module unload: FDynamicModule::Unload() -> FModuleInterface::Shutdown() -> FPlatformFreeLibrary -> removal from FModularDomain list.

## Integration
Modular/ system is the startup and plugin backbone used by the entire Engine. Thread/ FModularServices::RegisterService/GetService may be called from worker threads during async module loading. Memory/ FModularDomain and FModuleInfo allocations are tracked by FMemoryPool and FTrackingAllocator. Diagnostic/ FLogger logs module load/unload events via FLogger::Log with ELoggerVerbosity::Log. IO/ FArchive serializes FModuleInfo and FModuleStaticRegistration data for save/load of module state. Maths/ none directly, but FTransform and FQuaternion may be serialized as module data. Container/ TArray<FModuleInfo> stores the module registration list within FModularDomain. HAL/ PlatformFile may be loaded dynamically via FDynamicModule on console platforms. IO/ FString module names and FFileSystemToken paths are used for module resolution. Maths/ BIH/ Octree spatial data may be serialized as part of module content. Container/ TVector and TArray store the per-phase module lists within FModularDomain. The Modular/ModuleInterface.h header defines the contract every module must implement, and PPE_MODULE(...) is the macro used to statically register modules in and Source/Runtime/.
