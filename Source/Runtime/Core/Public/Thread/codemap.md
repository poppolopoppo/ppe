# Source/Runtime/Core/Public/Thread/

## Responsibility
This folder implements the Engine's threading and concurrency infrastructure, providing the foundational primitives for multi-threaded task execution, fiber-based scheduling, synchronization primitives, and lock-free data structures. It owns the central task manager, thread pools, completion ports, fiber pool, atomic operations, and all concurrency-building blocks used across the Engine. The Thread folder is the primary coordination point for parallel work, enabling efficient utilization of multi-core systems through a fiber-completionport scheduling model.

## Design
Threading design centers on the task-fiber completion port model: FTaskManager is the central task dispatcher that manages a pool of worker threads and assigns FTask objects to FFiber instances drawn from FTaskFiberPool. Fibers are user-mode coroutines that map onto OS threads via FPlatformThread, enabling cooperative multitasking without OS thread preemption overhead. Thread pools (FGlobalThreadPool, FIOThreadPool, FHighPriorityThreadPool, FBackgroundThreadPool) are TSingleton<FTaskManager, PoolType> instances, each specialized for workload type (IO, high-priority, background). Lock-free structures (TConcurrentQueue, TConcurrentHashMap, TMPMCBoundedQueue, TAtomicPool, TAtomicRefPtrPool, TAtomicSet, TAtomicBitMask) provide MPMC-safe operations using platform intrinsics (Interlocked*, __atomic_*) for wait-free or lock-free progress. Synchronization primitives (FAtomicSpinLock, FAtomicOrderedLock, FAtomicReadWriteLock, FAtomicPhaseLock, FAtomicMaskLock, FAtomicTicketRWLock) offer various trade-offs between contention and throughput. Barriers (FSynchronizationBarrier, FWaitGroup) coordinate multi-threaded task groups. Critical sections (FCriticalSection) and read-write locks (FReadWriteLock) provide OS-backed synchronization for coarse-grained sections. Thread context (FThreadContext, FThreadContextStartup) provides per-thread state and auto-singleton management.

## Flow
Task submission: user code enqueues an FTask (or lambda) into FTaskManager's internal queue, typically via FTaskScheduler::Produce(priority, task, pport). Scheduling: FTaskScheduler (Private) pops tasks and assigns them to available FFiber instances from the fiber pool. Fiber execution: each fiber runs its task, potentially posting dependent tasks back to FTaskManager via FCompletionPort. Completion: when all dependent tasks are posted, the signaling fiber writes to FCompletionPort, unblocking waiting threads. Worker threads call Consume() which pops tasks from their local worker queue; if empty, they wait on the condition variable _onTask. Lock-free queue operations: TConcurrentQueue::Enqueue/Dequeue use atomic compare-and-swap for wait-free or bounded wait-free progress. Atomic pool: TAtomicPool::Allocate/Deallocate uses interlocked fetch-and-add/fetch-and-and for per-thread slab management. Barrier wait: FSynchronizationBarrier::Wait increments a generation counter; threads block until their generation matches. WaitGroup: FWaitGroup::Add(delta) decrements a counter; Wait() blocks until zero. CriticalSection scope: FCriticalSection enters OS critical section via platform primitives; RAII scope exits on destruction, guaranteeing release.

## Integration
Thread/ infrastructure is cross-referenced by every other subsystem. Container/ TThreadSafe<T, Barrier> uses FAtomicMaskLock and FSynchronizationBarrier for lock-free access. Allocator/ FTrackingAllocator and FSlabAllocator are used per-thread for lock-free allocation. Memory/ TInSituPtr and TWeakPtr are used in lock-free data structures for safe hazard-pointer semantics. Maths/ TScalarVector operations may be called from multiple threads with external synchronization. IO/ FFileSystem and FArchive use FThreadPool for async file reading. Diagnostic/ FLeakDetector's FBlockTracker is thread-safe via FAtomicBitMask. HAL/ PlatformThread creates the OS threads that FTaskScheduler and FGlobalThreadPool manage. Modular/ FModularServices may be called from worker threads during module load. The Thread/Fiber.h header defines the fiber entry point used by FTaskFiberPool. FString and FText are not thread-safe and require external synchronization when accessed from multiple threads.
