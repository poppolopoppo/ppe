# Source/Runtime/Network/Private/Http/

## Responsibility
The Private HTTP folder implements the detail-level infrastructure underlying the public HTTP API, containing the buffered socket wrapper, handshake mechanisms, and request/response processing logic not exposed in the public header hierarchy. This folder provides the concrete implementation of `FSocketBuffered` for efficient HTTP-level I/O, `FHandShaker` variants for protocol upgrades (WebSocket upgrade, TLS negotiation), and the per-connection servicing context `FServicingPort` as used by the HTTP server. The design separates public HTTP API (`Source/Runtime/Network/Public/Http/`) from private detail (`Source/Runtime/Network/Private/Http/`), enabling protocol implementation specifics while maintaining a stable public interface. All types in this folder support the `FHttpServer` worker pool model and are called from the server's event loop during request processing.

## Design
Key patterns include the buffered I/O pattern where `FSocketBuffered` provides a slab-allocated read buffer (typically 8KB or configurable size) filled from the underlying socket via `recv()`, with read position tracking allowing multiple `Read()` calls to consume data from a single `recv()` invocation; the handshaker strategy pattern where `FHandShaker` defines a virtual `Dispatch()` method invoked during connection setup, with derived classes `FWebSocketHandShaker` (performs HTTP upgrade with `Sec-WebSocket-Key` exchange) and `FTLSHandShaker` (performs TLS handshake via platform crypto APIs); the request-response cycle pattern where `FHttpServer` worker loop reads `FHttpRequest` from the buffered socket, dispatches to the virtual `OnRequest()` hook, and writes `FHttpResponse` back through the same buffered channel; the keep-alive pattern where `FServicingPort` tracks connection idle time and decides whether to persist the `FSocketBuffered` connection or close it based on `FHttpServer::KeepAliveTimeout()`. Private types use detailed `FString` management for header names/values and are not for direct client consumption.

## Flow
HTTP request processing flow: `FHttpServer` worker calls `FListener.Accept()` → wraps socket in `FSocket` and `FSocketBuffered` → creates `FServicingPort(UID, handShaker, socket)` → invokes `handShaker.Dispatch()` to perform protocol upgrade (or no-op if plain HTTP); the servicing loop reads data via `FSocketBuffered::Read()` until a complete `FHttpRequest` is assembled; dispatches to `OnRequest(FServicingPort&, FHttpRequest&)` virtual hook; generates `FHttpResponse` with status, headers, and body; writes response via `FServicingPort.WriteResponse()` which transmits through `FSocketBuffered::Write()`; checks keep-alive timeout and either persists the connection for next request or calls `OnDisconnect()` and closes the connection. Response writing flow: `FHttpResponse` serialization via `FJsonSerializer` or direct `FBinarySerializer` output → `FServicingPort::WriteResponse()` → `FSocketBuffered::Write()` → platform `send()` → data transmitted to client.

## Integration
Connects to `Source/Runtime/Network/Private/Socket/` as `FSocketBuffered` and `FHandShaker` depend on socket primitives from the Private Socket folder. Connects to `Source/Runtime/Network/Public/Http/` as the public HTTP types are implemented by detail classes in this folder. Connects to `Source/Runtime/Remoting/` as `FRemotingServer` uses private `FHandShaker` and `FServicingPort` for request handling and protocol upgrades. Connects to `Source/Runtime/VFS/` as HTTP response bodies may contain serialized transactions loaded from VFS.
