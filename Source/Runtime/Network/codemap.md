# Source/Runtime/Network/

## Responsibility
The Network folder provides a comprehensive networking stack for the PPE runtime, encompassing TCP socket wrappers (`FSocket`), listener/acceptor infrastructure (`FListener`), HTTP server and client (`FHttpServer`, `FHttpClient`), per-connection service contexts (`FServicingPort`), handshake and protocol upgrade mechanisms (`FHandShaker`), and network utility types (`FAddress`, `FUri`). The layer supports both blocking and buffered operation models, with `FSocketBuffered` providing efficient HTTP parsing through a buffered socket wrapper. The design separates low-level socket operations from protocol-level handshaking and request/response processing, enabling protocol upgrades (WebSocket, TLS) via the `FHandShaker` abstraction. A `FNetworkModule` singleton manages module lifecycle, initialization, and shutdown. This folder is the primary network abstraction layer used by Remoting for HTTP-based endpoint exposure and by all modules requiring network connectivity.

## Design
Key patterns include the servicing port abstraction (`FServicingPort`) that decouples connection handling from protocol logic, the handshaker pattern supporting protocol upgrades (WebSocket, TLS) through `FHandShaker`, and RAII connection scopes (`FConnectionScope` for `FSocket` and `FListener`) that auto-connect and auto-disconnect. `FSocket` encapsulates a platform socket handle with timeout control and Nagle algorithm control via `SetNagleEnabled()`. `FListener` provides `Accept()` over both `FSocket` and `FSocketBuffered` variants, supporting both synchronous and asynchronous accept patterns. `FHttpServer` uses a worker pool model with `Start(workerCount)` and virtual callback hooks (`OnConnect`, `OnRequest`, `OnDisconnect`), enabling concurrent request handling. `FHttpClient` maintains persistent connections via `FSocketBuffered` and supports cookie/post maps for stateful HTTP interactions. `FServicingPort` per-connection context holds a `FGuid` UID, `FHandShaker` owner, and `FSocketBuffered` socket, with keep-alive timeout management and state transitions (Active → Idle → Closed). Network addresses use `FAddress` with `FString` host representation and service name enumeration for well-known port mapping. `FSocketBuffered` employs a slab-based read buffer for efficient HTTP header and body parsing.

## Flow
Control flow for HTTP server: `FHttpServer.Start(workerCount)` spawns a worker pool; each worker's event loop triggers `FListener.Accept()` producing an `FSocket` (or `FSocketBuffered`), which wraps the raw handle into a `FServicingPort` per-connection context. The handshaker dispatch loop calls `FHandShaker.Dispatch()` which invokes the `FServicingPort.KeepAlive()` check and protocol-specific processing. Request reading flows `FServicingPort.Servicing(ITaskContext& ctx)` → `OnRequest(FServicingPort&, FHttpRequest&)` → response writing via `Write response` → `OnDisconnect()`. For HTTP client: `FHttpClient.Get/Head/Post(uri)` → `FSocketBuffered` persistent connection → `Process(request)` → read response → `FHttpResponse` return. Connection teardown follows RAII scope destructors: `FConnectionScope` destructor calls `Disconnect()`, cleanup callbacks run, and the `FServicingPort` is returned to the pool or destroyed. Socket connection flow: `FSocket.Connect(address)` → platform `connect()` → `FSocket.SetTimeouts()` → read/write loops → `FSocket.Disconnect()` → platform `closesocket()`.

## Integration
Connects to `Source/Runtime/Remoting/` as `FRemotingServer` uses `FHttpServer` for transporting remoting requests; `FRTTIEndpoint`/`FSwaggerEndpoint` register HTTP routes via the `FHttpServer`; `FRemotingContext` carries per-request network state including `FRemotingCookieMap`, `FRemotingPostMap`, and `FRemotingQueryMap`. Connects to `Source/Runtime/VFS/` as HTTP responses can carry serialized transactions (JSON/binary) that may be loaded/stored via `FVirtualFileSystem`. Connects to `Source/Runtime/RTTI/` as RTTI data may be serialized over HTTP transports.
