# Source/Runtime/

## Responsibility
Source/Runtime/ aggregates the core engine libraries and runtime systems that form the foundation of the PPE game engine. This folder encompasses 8 core modules: Core (foundation: containers, math, memory, threading, IO, HAL, meta-programming, diagnostics), Application (windowing, input, UI, platform application layer), RHI (Rendering Hardware Interface - API-agnostic rendering abstraction), RTTI (Runtime Type Information and reflection), Serialize (multi-format serialization: binary, JSON, markup, FAT, Text), VFS (Virtual File System with mount points and trie resolution), Network (socket and HTTP client/server), and Remoting (RTTI-driven HTTP API with automatic OpenAPI/Swagger generation). Runtime/ provides the essential services and abstractions that all other engine subsystems depend on, including the fiber-based task scheduler, 36 custom allocator types, 68 math types, and the type-safe service registry (FModularServices).

## Design
Source/Runtime/ follows a modular design with 8 independently loadable modules, each with a well-defined interface declared in `*-module.json` and managed by the Go-based build system. The module lifecycle follows the pattern: Start(domain) → PostStart(domain) → DutyCycle(domain) → PreShutdown(domain) → Shutdown(domain) → ReleaseMemory(domain). Core/ serves as the foundational layer providing 62 container types (TVector, TArray, TDeque, TStack, TList, TIntrusiveList, TIntrusiveAVL, TIntrusiveWAVL, TRingBuffer, TSparseArray, etc.), 68 math types (TScalarVector, TScalarMatrix, TQuaternion, FTransform, FBIH, Octree, SH functions), and custom allocators (FMallocBinned, FMallocMipMap, FBitmapAllocator, FCascadedAllocator, FSlabHeap, FBucketAllocator, FInSituAllocator, FPageAllocator, FVirtualAllocator, FStackLocalAllocator, FTrackingAllocator, FStlAllocator, FSystemAllocator, FStaticAllocator, FFreeListAllocator). Application/ builds on Core for windowing and input via FPlatformFile and FPlatformThread. RHI/ provides an API-agnostic rendering abstraction that RHIVulkan/ implements specifically. RTTI/ generates reflection metadata driving serialization, UI binding, and REST API generation. Serialize/ supports 5 format backends (Binary, JSON, Markup, FAT, Text) with a runtime-defined DSL grammar. VFS/ provides trie-based mount point resolution with ASSOCIATIVE_VECTORINSITU inline storage. Network/ handles socket and HTTP operations. Remoting/ offers RTTI-driven HTTP API with automatic OpenAPI/Swagger generation. The design uses C++ templates, CRTP, expression templates, constexpr, and macro-based code generation extensively, with zero STL in hot paths.

## Flow
Source/Runtime/ data and control flow follows the module initialization and execution lifecycle. At startup, Core initializes first providing foundational containers, math types, and allocators; then Application starts windowing and input handling; RHI initializes the rendering backend (with RHIVulkan providing Vulkan implementation); RTTI generates reflection metadata used by Serialize for format-driven serialization; VFS mounts file systems and resolves paths; Network initializes socket/HTTP capabilities; Remoting registers the RTTI-driven HTTP API service. During each DutyCycle, the fiber-based task scheduler (FTaskManager with FTaskScheduler work-stealing) processes queued tasks across the thread pool. I/O operations flow through FBufferedStreamReader/FBufferedStreamWriter (64KB default buffers) which yield the fiber during blocking operations, allowing other tasks to execute. Serialization data flows through the DSL grammar (Lexer → Parser → AST → Serializer) with 5 format backends. Remoting exposes the RTTI metadata via HTTP for REST API consumption. At shutdown, modules reverse through PreShutdown → Shutdown → ReleaseMemory in deferred cleanup. Cross-module communication uses FModularServices with FReadWriteLock for thread-safe service access, and dependency order is controlled by LoadOrder in module JSON files.

## Integration
Source/Runtime/ integrates with all other top-level source folders. Core/ provides containers, math, and allocators used by Source/Extensions/RHIVulkan/ (Vulkan memory management, descriptor sets) and Source/Extensions/ApplicationUI/ (ImGui resource caches). Application/ connects to Source/ContentPipeline/ for asset import tools and Source/Programs/ for demonstration executables. RHI/ integrates with Source/Extensions/RHIVulkan/ for the Vulkan backend implementation and with Source/Programs/ (VoxelCube, ShaderToy for rendering demos). RTTI/ drives Source/Runtime/Serialize serialization format generation and Source/Runtime/Remoting/Private/Remoting automatic OpenAPI/Swagger generation; it also feeds Source/Extensions/ApplicationUI/ for ImGui binding. Serialize/ connects to Source/Runtime/VFS for file-based asset I/O and to Source/ContentPipeline/ for processed asset output. VFS/ supports path resolution for Source/ContentPipeline/ asset processing, Source/Tools/IOWrapper/ for distributed build file system wrapping, and Source/Programs/ for file-based demos. Network/ integrates with Source/Runtime/Remoting/Private/Remoting for HTTP API services and can be used by Source/Programs/ for networked gameplay. Remoting/ depends on RTTI/ for metadata exposure and integrates with Source/Runtime/Application/Public/Application for service registry endpoints. Specific paths: Source/Runtime/Core/ → Source/Extensions/RHIVulkan/ (memory allocators, compressed pairs), Source/Runtime/Application/ → Source/Extensions/ApplicationUI/ (windowing, ImGui), Source/Runtime/RHI/ → Source/Extensions/RHIVulkan/ (Vulkan implementation), Source/Runtime/Serialize/ → Source/ContentPipeline/ (asset format conversion), Source/Runtime/VFS/ → Source/Tools/IOWrapper/ (distributed build file wrapping), Source/Runtime/Network/ → Source/Runtime/Remoting/Private/Remoting (HTTP API infrastructure).
