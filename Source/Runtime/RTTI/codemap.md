# Source/Runtime/RTTI/

The Root RTTI folder aggregates metadata reflection for the entire PPE runtime. It houses the public-facing type descriptors (FMetaClass, FMetaProperty, FMetaEnum, FMetaFunction, FMetaObject) and the private implementation details (FMetaDatabase, FAtom, FAny) that power runtime type identification, property access, and transactional serialization. This folder is the foundation for all downstream systems: serialization formats depend on FMetaObject property traversal, remoting exposes the FMetaDatabase via FRTTIEndpoint, and the VFS uses FMetaObject for transactional file operations. The directory map below links to each sub-folder's codemap for cross-module navigation.

## Responsibility

This folder owns the complete RTTI reflection hierarchy that enables runtime type introspection, property/function enumeration, and type-erased data representation (FAtom/FAny) across the engine. FMetaDatabase serves as the singleton registry for all classes, enums, objects, and transactions, while FMetaClass, FMetaProperty, FMetaEnum, and FMetaFunction describe the structure and behavior of individual types. FAtom provides type-erased references with PTypeTraits, and FAny offers a small-buffer-optimized type-erased container. Private sub-folders implement the concrete metadata (MetaClass.cpp, MetaDatabase.cpp, MetaObject.cpp, etc.) and the RTTI module registration macros (RTTI_CLASS_HEADER, RTTI_ENUM_HEADER, RTTI_MODULE_DECL) that populate the database at module init. The folder is not itself a serializer but provides the metadata that all serializers (FBinarySerializer, FJsonSerializer, FTextSerializer, FFATSerializer, FMarkupSerializer) rely on for (de)serialization decisions.

## Design

Key abstractions include the singleton FMetaDatabase read/write guards (FMetaDatabaseReadable, FMetaDatabaseReadWritable) that protect concurrent access during game-world serialization, the atom-based type erasure model where FAtom = void* + PTypeTraits enabling uniform serialization across heterogeneous types, and the facet system (FMetaClassFacet, FMetaPropertyFacet, etc.) for extensible metadata extension without class modification. The macro-driven registration pattern (RTTI_CLASS_HEADER, RTTI_ENUM_HEADER, RTTI_MODULE_DECL) ensures compile-time registration of all RTTI types into FMetaDatabase. FMetaObject is ref-counted with an _outer SCMetaTransaction parent, forming a ownership tree that mirrors the transaction lifecycle (Unloaded → Loading → Loaded → Mounting → Mounted). FAny's small-buffer optimization (3×intptr_t in-situ storage) avoids heap allocation for common type-erased values. Private folders implement detailed metadata parsing, comparison, and hierarchy traversal logic.

## Flow

Data flow originates at module initialization where RTTI_MODULE_DECL macros register FMetaClass/FMetaEnum/FMetaFunction/FMetaProperty instances into the singleton FMetaDatabase. At runtime, FMetaObject::RTTI_Property(name) returns FAtom values that carry type-erased data via PTypeTraits, and FMetaObject::RTTI_Function(name) returns FMetaFunction* for invocation. Serialization flow: FTransactionSerializer → BuildTransaction → FLexer/Parser → AST → FParseContext → FAtom → FMetaObject property traversal → ISerializer.Serialize(). Remoting flow: FRTTIEndpoint → FMetaDatabase → JSON via FOpenAPI/FJsonSerializer. Transaction lifecycle: FMetaTransaction Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded, with FLinearizedTransaction flattening cross-references. Property access: FMetaProperty::Get() reads/writes typed data through FAtom.

## Integration

This folder integrates with all Runtime modules via real paths under Source/: Source/Runtime/Serialize/ for format serializers (FBinarySerializer, FJsonSerializer, FTextSerializer, FFATSerializer, FMarkupSerializer) that depend on FMetaObject/FMetaProperty for property-level (de)serialization; Source/Runtime/Network/ and Source/Runtime/Remoting/ where FRTTIEndpoint exposes the entire FMetaDatabase via auto-generated REST API; Source/Runtime/VFS/ where FMetaObject enables transactional file operations; Source/Runtime/Application/ and ContentPipeline modules that use RTTI_MODULE_DECL for module registration. Specific paths: Source/Runtime/RTTI/Public/MetaClass.h, Source/Runtime/RTTI/Public/MetaProperty.h, Source/Runtime/RTTI/Public/MetaObject.h, Source/Runtime/Serialize/Public/Binary/BinarySerializer.h, Source/Runtime/Serialize/Public/Json/JsonSerializer.h, Source/Runtime/Serialize/Public/Text/TextSerializer.h, Source/Runtime/Remoting/Public/Remoting/RTTIEndpoint.h, Source/Runtime/VFS/Public/VirtualFileSystem.h, Source/Runtime/Remoting/Public/RemotingEndpoint.h All modules depend on the RTTI foundation through RTTI_MODULE_DECL and FMetaDatabase access patterns.
