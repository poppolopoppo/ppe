# Source/Runtime/RTTI/Private/RTTI/

The Private RTTI sub-folder implements the concrete type definitions and macro infrastructure that populate the FMetaDatabase singleton. While the Public/RTTI/ folder provides the declarations and macro definitions, this folder contains the actual implementations and detailed type layouts that the macros expand into. MetaClass.cpp, MetaDatabase.cpp, MetaObject.cpp, MetaProperty.cpp, MetaEnum.cpp, MetaFunction.cpp, and MetaTransaction.cpp are the real workhorses here — they implement the FMetaClass property enumeration, FMetaDatabase singleton management, FMetaObject ref-counting, FMetaProperty offset-based get/set, FMetaEnum value↔string conversion, FMetaFunction invoke thunk, and FMetaTransaction state machine respectively. The RTTI_MODULE_DECL macro defined in this folder is what each module's .cpp uses to register its types; without the expansions in this folder's .cpp files, the reflection system would have no substance. This folder also contains the detail headers (NativeTypes.h, NativeTypes.List-inl.h, etc.) that support the internal data structures of the metadata objects.

## Responsibility

This folder owns the concrete implementation that makes RTTI types substantive. The .cpp files here (MetaClass.cpp, MetaDatabase.cpp, MetaObject.cpp, etc.) are where the actual data structures, algorithms, and lifetime management for the reflection system live. MetaDatabase.cpp implements the FMetaDatabase singleton with its HashMap registries for classes, enums, objects, transactions, and modules, including the read/write guard mechanisms. MetaClass.cpp implements property enumeration, inheritance traversal, and instance creation. MetaObject.cpp implements ref-counting and the transaction _outer linking. MetaProperty.cpp implements offset-based property access with PTypeTraits. MetaEnum.cpp implements string↔ordinal conversion. MetaFunction.cpp implements the invoke thunk mechanism. MetaTransaction.cpp implements the Load/Mount/Mounted/Unmount/Unload state machine. The RTTI_MODULE_DECL macro, defined through the detail headers in this folder, is what each module's .cpp calls to register its types into the global FMetaDatabase. Without this folder's implementations, the reflection system would be purely declarative with zero runtime data.

## Design

The design centers on the FMetaDatabase singleton as the central registry, implemented in MetaDatabase.cpp using ASSOCIATIVE_VECTORINSITU hash maps (sorted vectors) for _classes, _enums, _objects, _transactions, and _modules, providing both fast lookup and sorted iteration. FMetaObject is ref-counted with an _outer pointer linking to SCMetaTransaction, creating an ownership tree that mirrors the transaction lifecycle (Unloaded→Loading→Loaded→Mounting→Mounted). Property data flows through FAtom (void* + PTypeTraits), enabling type-erased read/write across heterogeneous types without knowing the concrete type at compile time. The facet system (FMetaClassFacet, etc.) is implemented here as a mechanism for adding behavior to FMetaClass without modifying the core struct. All .cpp implementations are DLL-safe with DLL_IMPORT/EXPORT guards and use the detail headers (NativeTypes.h, NativeTypes.List-inl.h, etc.) for internal data structures like TMap, TVector, TString, and TRefPtr. The small-buffer optimization in FAny (3×intptr_t in-situ storage) is defined in the private detail headers and used throughout the metadata system.

## Flow

Flow begins when a module's .cpp includes the RTTI detail headers and calls RTTI_MODULE_DECL, which expands to register the module's FMetaClass/FMetaEnum/FMetaFunction/FMetaProperty objects into the singleton FMetaDatabase. The macro expansion happens at link time, so all modules must be linked together for the registration to be complete. At runtime, code can query FMetaDatabase::Get() to find types, enumerate properties, create instances, or invoke functions. Serialization flow: FTransactionSerializer → BuildTransaction → FMetaDatabase→FindClass→FMetaClass→_propertiesAll→FMetaProperty→Get()→FAtom→ISerializer output. Transaction lifecycle: FMetaTransaction Load() → Mount() → Mounted, Unmount() → Unload() → Unloaded, with FLinearizedTransaction flattening cross-references for deserialization. Remoting: FRTTIEndpoint → FMetaDatabase → JSON via FOpenAPI/FJsonSerializer. The flow is: module init → FMetaDatabase population → runtime queries → property/function access → serialization/remoting output.

## Integration

This folder integrates directly with the Public RTTI folder and all modules that use reflection. Downstream: Source/Runtime/RTTI/Public/RTTI/ where the macro definitions and type declarations live; Source/Runtime/RTTI/Public/ where the public type descriptors (FMetaClass, FMetaProperty, etc.) are consumed; Source/Runtime/Serialize/Public/ and Source/Runtime/Serialize/Private/ where all format serializers (FBinarySerializer, FJsonSerializer, FTextSerializer, FFATSerializer, FMarkupSerializer) depend on the concrete metadata implementations for property-level (de)serialization; which reads the FMetaDatabase for auto-generated REST API; Source/Runtime/VFS/ where FMetaObject enables transactional file operations. Specific paths: Source/Runtime/RTTI/Public/RTTI.h, Source/Runtime/RTTI/Public/RTTI_fwd.h, Source/Runtime/RTTI/Public/RTTIModule.h, Source/Runtime/RTTI/Private/MetaClass.cpp, Source/Runtime/RTTI/Private/MetaDatabase.cpp The RTTI_MODULE_DECL macro is the integration point connecting this folder to every module in the project.
