# Source/Runtime/RTTI/Public/

The Public RTTI folder exposes the core type-descriptor interfaces that external modules and tools use for reflection without requiring private implementation headers. FMetaClass, FMetaProperty, FMetaEnum, FMetaFunction, and FMetaObject are the primary public types; FMetaDatabase is a singleton accessible via FMetaDatabase::Get(). All types follow the macro-driven registration pattern (RTTI_CLASS_HEADER, RTTI_ENUM_HEADER, RTTI_FUNCTION_HEADER, RTTI_PROPERTY_HEADER, RTTI_OBJECT_HEADER) that populate the FMetaDatabase at module startup. Forward declarations and type definitions are in RTTI_fwd.h and RTTI.h, with module-level declarations in RTTIModule.h. This folder is intentionally minimal in the public API - all heavy implementation lives in the Private sub-folder, but the public types are sufficient for property access, enum conversion, function invocation, and object creation via CreateInstance(). External systems (remoting, serialization, VFS) interact with these types through well-defined interfaces that have remained stable across engine versions.

## Responsibility

This folder owns the public-facing RTTI type descriptors that form the contract between the reflection system and all downstream consumers: serialization formats, remoting endpoints, the virtual file system, and user code. FMetaClass describes a class's properties, functions, inheritance, and facets; FMetaProperty describes a single property with offset, traits, and flags (public/private/readonly/dynamic/transient); FMetaEnum describes enum values with string↔ordinal conversion; FMetaFunction describes a callable function with parameters and return type; FMetaObject is the base class for all RTTI-enabled objects, ref-counted and supporting load/unload cycles. FMetaDatabase singleton provides global query access (GetClass, GetEnum, GetObject, GetTransaction, GetModule). The public API is deliberately header-light, forwarding to private implementations where needed, but it must remain stable across engine iterations since remoting (FRTTIEndpoint) and serialization (FBinarySerializer/FJsonSerializer/FTextSerializer) all depend on these type names and semantics.

## Design

The design centers on the type-erased property access pattern: FMetaProperty carries offset, traits, and flags, and its Get() method reads/writes data through an FAtom wrapper that bundles a void* pointer with PTypeTraits for type information. FMetaClass maintains _propertiesAll (HashMap<FName, FMetaProperty*>) and _propertiesSelf (VectorInSitu<FMetaProperty>) for property lookup, with Parent() virtual for inheritance traversal. FMetaEnum provides ValueToString() and StringToValue() conversions with ETypeId flags for bitmask operations. FMetaFunction stores an invoke thunk and parameter type information, enabling runtime reflection-based function calls. All public types are designed for safe cross-DLL use (DLL_IMPORT/EXPORT) and are header-only compatible with the macro system (RTTI_CLASS_HEADER, etc.) that performs compile-time registration into FMetaDatabase. The facet system (FMetaClassFacet, etc.) extends type behavior without modifying core structures.

## Flow

Flow begins at module startup where RTTI_CLASS_HEADER, RTTI_ENUM_HEADER, RTTI_FUNCTION_HEADER, RTTI_PROPERTY_HEADER, and RTTI_OBJECT_HEADER macros expand to register each type's FMetaClass/FMetaEnum/FMetaFunction/FMetaProperty into the singleton FMetaDatabase. At runtime, client code calls FMetaDatabase::Get()->FindClass(name) → FMetaClass*, then iterates _propertiesAll or calls RTTI_Property(name) → FAtom. Property Get() reads typed data via PTypeTraits; Set() writes back. Function invocation: FMetaFunction::Invoke() with parameter FAny values. Object creation: FMetaClass::CreateInstance() → PMetaObject. Serialization flow: ISerializer → FMetaClass→_propertiesAll → FMetaProperty→Get() → FAtom → typed memory read/write. Remoting: FRTTIEndpoint → FMetaDatabase → JSON via FOpenAPI/FJsonSerializer. Transaction: FMetaObject::_outer links to SCMetaTransaction, enabling load/unload lifecycle.

## Integration

This folder integrates with adjacent modules via real paths under Source/. Downstream consumers: Source/Runtime/Serialize/Public/ where FBinarySerializer, FJsonSerializer, FTextSerializer, FFATSerializer, FMarkupSerializer all use FMetaClass/FMetaProperty for property-level (de)serialization; exposes the entire FMetaDatabase via auto-generated REST API; Source/Runtime/VFS/ where FMetaObject enables transactional file operations; Source/Runtime/Network/ where HTTP responses can carry serialized RTTI data. Specific paths: Source/Runtime/RTTI/Public/MetaClass.h, Source/Runtime/Serialize/Public/Binary/BinarySerializer.h, Source/Runtime/Serialize/Public/Json/JsonSerializer.h, Source/Runtime/Serialize/Public/Text/TextSerializer.h, Source/Runtime/Remoting/Public/Remoting/RTTIEndpoint.h, Source/Runtime/VFS/Public/VirtualFileSystem.h, Source/Runtime/Remoting/Public/RemotingEndpoint.h All modules ultimately depend on the RTTI foundation through FMetaDatabase::Get() and the macro registration pattern.
